# CLaaS2SaaS SemantIQ — Functional Specification

**Document ID:** 02-Functional-Specification
**Derived from:** 01-Requirement-Scoping
**Status:** Draft for review

## Scope and conventions

One row specifies one functional capability. Features are grouped by the delivery cluster
they belong to. Cluster 0 covers the platform capabilities that the 80-step procedure
assumes but does not itself list — sign-in, tenant onboarding, and the engine that runs the
steps.

**Actors** are the SemantIQ application roles defined in 00-Solution-Architecture section 7:
Platform Administrator, Tenant Administrator, Lead Data Engineer, Data Engineer, Business
User. *System* denotes unattended execution by a queued job.

**Assumptions are labelled inline.** Where a Microsoft API is required but its availability
or service-principal support must be confirmed against the current service, the
precondition says so rather than asserting it.

## Cluster 0 — Platform Foundation

|---|---|---|---|---|---|
| Microsoft Sign-In | Authenticates users against Microsoft Entra ID and establishes a SemantIQ session bound to their tenant. | All roles | SemantIQ app registration exists; the customer tenant has granted admin consent; the host serves valid HTTPS. | 1. User selects Sign in with Microsoft.<br>2. System redirects to Entra ID with the authorization-code flow and PKCE.<br>3. User authenticates and, on first use, an administrator grants consent.<br>4. System validates the returned tokens and resolves the user's tenant.<br>5. System creates or updates the local user record and assigns the default role.<br>6. System stores the refresh token encrypted and opens the session. | The user holds an authenticated session scoped to one tenant, with a refresh token available server-side for delegated Fabric calls and never exposed to the browser. |
| Tenant Onboarding | Registers a customer tenant and confirms that SemantIQ holds the access it needs to operate. | Platform Administrator, Tenant Administrator | The signing-in user holds an administrator role in the customer tenant. | 1. Administrator initiates onboarding.<br>2. System records tenant identity and display name.<br>3. System requests the required scopes and records the consent outcome.<br>4. System runs a connectivity probe against each required Microsoft endpoint.<br>5. System reports any endpoint that is unreachable.<br>6. Administrator confirms the tenant record. | The tenant is registered, consent state is recorded, and any blocked Microsoft endpoint is reported before project work begins rather than discovered during it. |
| Capability Probe | Determines which Microsoft operations are available to this tenant, so each step's automation tier reflects reality rather than documentation. | System, Platform Administrator | Tenant onboarding is complete. | 1. System enumerates the operations the step catalogue depends on.<br>2. System performs a safe read or dry-run per operation.<br>3. System records availability, the identity type that worked, and the observed error for failures.<br>4. System resolves each step's effective tier from the results.<br>5. System reports any step demoted from A to B. | Every step's automation tier is grounded in what this tenant actually permits, and a demotion is surfaced to the project team instead of failing mid-run. |
| Project Setup | Creates the container for one customer initiative and selects the blueprint it will follow. | Lead Data Engineer, Tenant Administrator | Tenant onboarding is complete. | 1. User creates a project with name, sponsor and business objective.<br>2. User selects a blueprint template or the full 80-step blueprint.<br>3. System instantiates the stages and step runs in blocked or ready state.<br>4. System resolves each step's tier from the capability probe.<br>5. User confirms the project. | A project exists with its complete step plan, each step's tier resolved, and the readiness stage open for work. |
| Blueprint Runner | Executes the blueprint by advancing step runs through their state machine, handling automated operations, guided verification and recorded decisions. | System, Data Engineer, Lead Data Engineer | A project exists; at least one step is ready. | 1. System identifies steps whose dependencies are satisfied and marks them ready.<br>2. For a Tier A step, System queues its operations and polls each long-running operation to completion.<br>3. For a Tier B step, System presents the instruction and deep link, then runs the verification probe on request.<br>4. For a Tier C step, System collects the decision or artifact and routes it for approval.<br>5. System records every outcome as an audit event.<br>6. System advances or halts the run and refreshes dependent steps. | The blueprint progresses with each step in a known state, each transition audited, and a failure isolated to the step that caused it while independent steps continue. |
| Step Verification | Confirms that a step's intended outcome is genuinely present in Microsoft, rather than accepting a user's assertion. | System | The step defines at least one verification probe. | 1. System reads the current state from the relevant Microsoft API.<br>2. System compares it against the step's expected state.<br>3. On match, System marks the step verified with the evidence.<br>4. On mismatch, System reports the specific difference and keeps the step open.<br>5. Where verification is impossible, System requires a written exception from a named approver. | A step is complete only on verified evidence or an approved written exception, and the evidence is retained for the go-live review. |
| Operation Retry and Resume | Recovers a failed or interrupted operation without duplicating work in the customer's Fabric tenant. | System, Data Engineer | An operation has failed or been interrupted. | 1. System classifies the failure as transient, permission, configuration or unknown.<br>2. For a transient failure, System retries with exponential backoff and jitter within the configured limit.<br>3. For any other class, System halts and reports the cause with the Microsoft error detail.<br>4. On resume, System re-checks the idempotency key before acting.<br>5. System records every attempt. | Transient failures self-heal, real failures stop with a diagnosable cause, and no retry ever creates a duplicate Fabric artifact. |
| Exception Register | Records an authorised deviation where a required step cannot be completed as specified. | Tenant Administrator, Platform Administrator | A step is blocked and cannot be completed as specified. | 1. User raises an exception against the step with a reason and a compensating control.<br>2. System routes it to a named approver.<br>3. Approver approves or rejects with comment.<br>4. On approval, System marks the step exception-approved and records it.<br>5. System includes the exception in the go-live readiness view. | Every deviation is visible, justified, attributed to a named approver, and unavoidably present at go-live review. |
| Audit Trail | Provides the immutable record of every change SemantIQ made or verified. | Tenant Administrator, Platform Administrator | Audit events exist. | 1. User opens the audit trail and filters by actor, project, step, target or date.<br>2. System returns matching events with actor, tenant, target, correlation ID and outcome.<br>3. User opens an event to see the payload digest and Microsoft response summary.<br>4. User exports the filtered set. | Any change can be traced to an actor, a time, a target and an outcome, and the record cannot be edited from within the application. |
| Recycle Bin | Holds soft-deleted SemantIQ records so a deletion is recoverable. | Data Engineer, Tenant Administrator | A record has been deleted. | 1. Deleting any record routes it to the recycle bin.<br>2. Owner restores their own records; Tenant Administrator restores any, bucketed by entity.<br>3. Permanent deletion is available to Tenant Administrator behind a confirmation naming the target.<br>4. Emptying everything requires a typed confirmation word. | Deletion is reversible by default, permanent deletion is gated to the administrator tier, and the destructive path carries deliberate friction. |
| Notification Service | Informs the right people when a step needs attention or an operation has failed. | All roles | Notification recipients are configured. | 1. System raises a notification on step failure, verification failure, awaiting-input, approval request or schedule breach.<br>2. System resolves recipients from role and project membership.<br>3. System delivers in-application and by email where configured.<br>4. User acknowledges or opens the originating record. | The person who can act on a blocked or failed step learns about it without needing to watch the application. |

## Keystone features in narrative form

Three features carry disproportionate weight. They are restated here in narrative form
because they will need the most design attention.

### Blueprint Runner

**Feature Name:** Blueprint Runner

**Description:** Executes a project's blueprint by advancing each of the 80 step runs
through an explicit state machine, dispatching automated Microsoft operations, presenting
guided instructions with verification, and collecting recorded decisions — while keeping
every transition auditable and every operation idempotent.

**Actors/Users:** System (unattended execution), Data Engineer and Lead Data Engineer
(supervision and input), Tenant Administrator (approvals and exceptions).

**Preconditions:** A project exists with an instantiated blueprint. The capability probe
has resolved each step's effective tier. At least one step is in `ready` state. Tenant
credentials are valid and the token broker can obtain a delegated token.

**Steps/Workflow:**

1. The runner evaluates dependencies and moves every satisfied step from `blocked` to
   `ready`.
2. For each ready Tier A step it enqueues the step's operations, each carrying a
   deterministic idempotency key.
3. Each operation issues its Microsoft call. If the response is a long-running operation,
   the job stores the operation URL and re-queues itself after the advertised delay
   instead of waiting.
4. On completion the operation runs its verification probe and records the evidence.
5. For a Tier B step the runner presents the required action, the deep link and the
   verification criteria, then moves the step to `awaiting_verification`. On request it
   runs the probe and either verifies the step or reports the precise difference.
6. For a Tier C step the runner collects the decision or artifact and routes it to the
   named approver.
7. Every transition writes an audit event with actor, target, correlation ID and outcome.
8. A failed step halts its own branch only. Independent branches continue.
9. Completed steps release their dependents, and the cycle repeats until the stage is
   complete or every remaining step is blocked or failed.

**Expected Outcome:** The blueprint advances as far as it can without supervision, every
step sits in a known and explainable state, no failure cascades beyond its own dependency
branch, no retry duplicates a Fabric artifact, and the complete run history is available as
audit evidence.

### Semantic Enrichment Workspace

**Feature Name:** Semantic Enrichment Workspace

**Description:** Captures a business description and business synonyms for every object in
the semantic model, measures coverage, and continuously absorbs new terminology from the
questions the agent failed to understand. This is the feature that most determines whether
the conversational application is useful.

**Actors/Users:** Data Engineer (primary), Business User (the authority on terminology),
Lead Data Engineer (approval).

**Preconditions:** The semantic model exists with business-friendly names applied and no
unresolved technical names. Relationships are validated. The AI surface has been drafted so
enrichment can be prioritised toward objects the AI will actually see.

**Steps/Workflow:**

1. The workspace lists every table, column and measure with its current description,
   synonym set and coverage state, prioritised by whether the object is inside the AI
   surface.
2. The Data Engineer writes a business description per object; the Business User reviews it
   for terminology, not grammar.
3. The Business User adds the synonyms and abbreviations people genuinely use, including
   informal and legacy terms.
4. The system reports description and synonym coverage as a percentage of the AI surface,
   and separately for the whole model.
5. Monitoring supplies candidate synonyms extracted from failed and low-confidence
   questions; each is queued for review with the question that produced it.
6. The reviewer accepts, edits or rejects each candidate.
7. Accepted changes are applied to the model and versioned.
8. The stage cannot complete until coverage of the AI surface meets the configured
   threshold.

**Expected Outcome:** Every object the AI can see carries a business description and the
synonyms real users say, coverage is measured rather than assumed, and the vocabulary keeps
widening from actual usage — which is what makes accuracy improve over time instead of
plateauing.

### Ground Truth Question Bank

**Feature Name:** Ground Truth Question Bank

**Description:** Maintains real business questions paired with independently approved
correct answers and tolerances, re-runs the whole bank on every relevant change, and turns
agent accuracy into a measured figure with a trend.

**Actors/Users:** Business User (supplies questions and approves answers), Data Engineer
(executes and diagnoses), Lead Data Engineer (threshold owner).

**Preconditions:** Measures are validated. The agent is testable. At least one named
business approver is available to certify expected answers.

**Steps/Workflow:**

1. The Business User adds a question in their own words, exactly as they would ask it.
2. The expected answer is established independently of the agent — from an existing report,
   a manual calculation or an authoritative system — and recorded with its tolerance.
3. A named approver certifies the expected answer, and the certification is dated.
4. The bank is executed as a suite: each question is asked, and the answer, generated query
   and confidence are captured.
5. Each result is scored against the expected answer within tolerance.
6. The suite reports an accuracy score and its trend against previous runs, with a
   per-question pass and fail history.
7. Failures route to the remediation tracker with their classification.
8. The full bank re-runs automatically on any change to the model, the agent, the AI surface
   or a business definition.
9. Publication is blocked while accuracy sits below the configured threshold.

**Expected Outcome:** Accuracy is a number with a history and an owner rather than an
impression, regressions are caught by the change that caused them, and publication is
