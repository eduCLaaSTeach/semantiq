## 1. Proposed Gate 4 architecture

### 1.1 One new module, two existing ones extended

```text
app/Modules/Governance/          NEW - the whole of gate 4
  Enums/
  Http/Controllers/
  Http/Requests/
  Models/
  Policies/
  Support/
app/Modules/Audit/               EXTENDED - a read/query surface beside the writer
app/Modules/Identity/            EXTENDED - the privacy contact on ADM-002
```

`Audit` gains a QUERY side. Today it is write-only by design: `AuditLogger`
writes, `AuditEvent` refuses updates and deletes. ADM-013 adds
`AuditQuery` - a read surface with its own redaction rules, which are NOT the
writer's rules. The writer protects the trail from secrets; the reader protects
the VIEWER from seeing more than their role justifies. Two different problems,
so two different classes.

### 1.2 The three patterns gate 3 established, reused rather than reinvented

| Gate 3 pattern | Gate 4 use |
|---|---|
| `SecurityStorage` schema readiness | `GovernanceStorage`, same shape, covering seven new tables |
| Catalogue-in-code (`config/security.php`) | `config/governance.php` for retention categories, classifications, geographies and deadlines |
| Derived status, never fixed text | Every profile and register computes its own state; no screen asserts a level it did not calculate |

### 1.3 Profiles are VERSIONED, not editable rows

**A data protection profile and a sovereignty profile are evidence.** An
auditor asks "what was in force on 3 March", and a mutable row cannot answer.

So: one ACTIVE profile per organisation, and superseding it writes a new row and
marks the old one `superseded` with the timestamp. Nothing is updated in place
once approved. A DRAFT may be edited freely until it is approved; after approval
it is immutable.

This is the single biggest structural decision in the gate. It is decision D4.

### 1.4 What gate 4 deliberately does NOT build

Stated so nobody looks for it later.

| Not built | Why | Where it goes |
|---|---|---|
| A retention EXECUTION engine | SEC-DEC-038: the audit triggers make routine deletion impossible by design. Policy and execution are different problems | A separately approved controlled operation |
| Email or push notification | No approved mail transport; `MAIL_MAILER=log` today | Gate 6, or a separate approval |
| Any PDPC transmission | External communication is a legal act, not an application feature | Out of scope permanently unless separately approved |
| Automatic correction of `audit_events` | Append-only. Never | Annotation instead, see 2.5 |
| Fabric geography enforcement | ADM-015 stores the approved profile; comparing a requested service region against it is Phase 02 | Phase 02 |

## 2. Feature-by-feature design

### 2.1 ADM-013 Audit Log

**Screen:** Audit Logs, Compliance cluster. Advanced table tier.
**Route:** `GET /admin/audit-logs`, plus `GET /admin/audit-logs/{auditEvent}` for
one event in full.

**Filters:** date/time range (UTC, with the viewer's time zone shown), actor,
action, module, resource type, resource id, outcome, correlation id, free text
over `reason`. All filters are server-side and indexed; see 3.9.

**Pagination:** keyset, not offset. `audit_events` is append-only and grows
without bound, and `OFFSET 40000` on a seven-year trail is a table scan. Keyset
on `(occurred_at DESC, id DESC)` uses the existing index.

**Redaction on READ - this is new and is not the writer's redaction.**

| Column | Shown to whom | Why |
|---|---|---|
| `action`, `module`, `outcome`, `occurred_at`, `correlation_id` | Anyone who may read the log | No personal data, no payload |
| `actor_label` (an email) | Anyone who may read the log | Naming who did it is the point of an audit trail |
| `before_summary` / `after_summary` | Anyone who may read the log | Already redacted at write time by `Redaction::summarise()` |
| `reason` | Anyone who may read the log | Already scrubbed at write time |
| **`ip_address`** | **`admin.audit.view_network` only** | An IP is personal data under the PDPA and is rarely needed. Separated so the common case does not carry it |
| `resource_id` | Anyone who may read the log | An opaque id. The screen does NOT join to resolve it into a person's name |

**No export in gate 4.** See decision D9.

**Retention interaction:** the screen states the retention category and policy
in force for `audit_events`, read from PDPA-03, and states that no application
path can delete from this table.

**Day-one empty state:** an audit trail is never empty on a live system - the
first sign-in writes to it. If it IS empty the screen says the trail is empty
and that this is unexpected on a running system, rather than showing a neutral
"no results".

### 2.2 ADM-014 Data Protection Profile

**Screen:** Data Protection Profile, Compliance cluster.
**Routes:** `GET/PUT /admin/data-protection`, `POST /admin/data-protection/approve`,
`POST /admin/data-protection/supersede`.

Not a switch. A profile record with these fields, all of which the product owner
named:

| Field | Type | Note |
|---|---|---|
| `regime` | choice | `pdpa_sg` today. NOT a boolean. Adding GDPR later is a catalogue entry |
| `regime_confirmed_on`, `regime_confirmed_by` | date, user | DEC-002 was a legal determination and the profile records who made it |
| `default_classification` | choice | Public / Internal / Confidential / Restricted |
| `purpose_statement` | text | Purpose limitation, in words. Free text because a purpose is not an enum |
| `personal_data_allowed` | boolean | Whether the control plane may hold personal data at all |
| `special_category_handling` | choice + text | `not_permitted` / `permitted_with_controls`, plus the controls |
| `masking_required` | boolean | |
| `export_policy` | choice | `prohibited` / `approval_required` / `permitted_logged` |
| `access_request_due_days` | integer | Feeds PDPA-01's due date. Configurable, with a stated basis |
| `correction_request_due_days` | integer | Same |
| `breach_assessment_due_hours` | integer | Feeds PDPA-02 |
| `pdpc_notification_due_days` | integer | **3 by default, and the field carries its basis.** Decision D7 |
| `individual_notification_required_when` | choice | `significant_harm` / `always` / `never` |
| `owner_user_id` | user | Policy owner |
| `effective_from`, `review_due_on` | date | |
| `status` | enum | `draft` / `active` / `superseded` |
| `approved_by_user_id`, `approved_at` | | |

**Personal-data categories and sensitivity classification** are NOT columns on
this profile - they are rows in `personal_data_categories`, because there are
many of them and each carries its own classification, lawful basis and retention
link. See 3.4.

**Relationship to the other features:** this profile is the SOURCE of the due
dates PDPA-01 and PDPA-02 use, and the retention categories in PDPA-03 point
back at its classifications. That is what makes it a profile rather than a page
of settings.

### 2.4 ADM-016 Sovereignty Exceptions

**Screen:** Exceptions, under Data Sovereignty. Register plus a detail page.
**Routes:** `GET /admin/sovereignty/exceptions`, `/new`, `/{exception}`,
`POST` for request, decide, revoke.

A workflow, not a checkbox:

```text
draft -> requested -> approved | rejected -> (expired | revoked)
```

| Field | Note |
|---|---|
| `reference` | Human-quotable, `SOV-EX-0001`, unique per organisation |
| `requested_capability`, `requested_geography` | |
| `data_classification` | From the ADM-014 classification list |
| `business_reason`, `risk_description` | Both required. A reason without a risk is a request nobody assessed |
| `requested_by_user_id`, `requested_at` | |
| `starts_on`, `expires_on` | **`expires_on` is required.** A permanent exception is a policy change, not an exception |
| `approver_user_id`, `decision`, `decision_reason`, `decided_at` | |
| `evidence_reference` | |
| `revoked_by_user_id`, `revoked_at`, `revocation_reason` | |
| `status` | Derived from dates and decision; never stored as a free choice |

**Rules that must hold:**
- The requester may not be the approver. Enforced in the service, not the form.
- Approving requires the ADM-010 re-authentication (extends `CriticalAction`).
- An expired exception does not silently continue. The sovereignty screen shows
  the profile as MODIFIED BY EXCEPTION only while an exception is `approved`
  and unexpired.
- **Exceptions never edit the profile.** The profile stays as approved; the
  exception is an overlay with an end date. This is what stops silent weakening.

### 2.5 PDPA-01 Personal Data Access and Correction

The hardest feature in the gate, and the one with the most decisions.

**Screens:** Privacy Requests register, request detail, response review.
**Routes:** `/admin/data-protection/privacy-requests`, `/new`, `/{request}`,
plus POST actions for verify, assemble, review, decide, complete.

```text
received -> identity_verification -> assembling -> in_review
         -> awaiting_decision (correction only) -> responded -> closed
                                                 \-> refused
```

#### The schema re-scan, which the plan was told to do

DEC-002 named five tables. **The actual answer is nineteen**, in four bands.

**Band A - the subject's own record.**

| Table | Personal data |
|---|---|
| `users` | name, email, `entra_object_id`, `entra_tenant_id`, `external_reference_id`, `last_signed_in_at`, access window, placement |
| `password_reset_tokens` | **email.** Unused today - there is no reset form - but the table exists and would hold an address |
| `sessions` | `user_id`, `ip_address`, `user_agent`. **Only when `SESSION_DRIVER=database`**, which it is not |

**Band B - records about the subject.**

| Table | Personal data |
|---|---|
| `audit_events` | `actor_user_id`, `actor_label`, `ip_address`, and `resource_id` when the subject is the resource |
| `domain_entitlements` | which business domains they may read |
| `user_roles` | which roles they hold |
| `access_review_items` | `user_id`, `subject_label`, `note`, decisions about them |

**Band C - attribution. The subject's name attached to somebody else's record.**

Every one of these carries `created_by_user_id`, `updated_by_user_id` or an
equivalent: `organisations`, `business_units`, `teams`, `roles`,
`role_permissions`, `access_reviews`, `system_settings`, `feature_flags`,
`security_policies`, `secret_references`. Plus `business_units.manager_user_id`,
`teams.lead_user_id`, `secret_references.owner_user_id`,
`access_review_items.decided_by_user_id`, `domain_entitlements.granted_by_user_id`,
`user_roles.assigned_by_user_id`, `access_reviews.opened_by_user_id`.

**Band D - free text that may name a person.**

`organisations.data_owner`, `organisations.privacy_contact`,
`organisations.security_contact`, `access_review_items.subject_label` and
`note`, `audit_events.reason`, `audit_events.before_summary` /
`after_summary`. Also `failed_jobs.payload` / `exception`, `jobs.payload` and
`cache.value`, which are incidental and unbounded.

**Gate 4's own new tables add a fifth band** - see 3.10. Privacy requests and
breach records are themselves personal data about the people named in them.

**Band C is the design problem.** "Alice approved Bob's Finance entitlement" is
personal data about Alice AND about Bob. Releasing it wholesale to Alice
discloses Bob. Withholding it entirely under-answers a lawful access request.
Decision D5.

#### How data is assembled

A `PrivacySubjectAssembler` with **one collector class per band**, each
declaring what it returns, its band, and its default disclosure treatment.
Registered in a catalogue, so adding a table to the scope is a code review -
the same reason the permission registry is code.

**A structural test asserts that every table in the schema is either claimed by
a collector or explicitly listed as out of scope with a reason.** This is the
control that stops the scope silently going stale as gates 5, 6 and 7 add
tables. It is the single most valuable test in the gate.

#### How unrelated individuals are excluded

Three treatments, decided per collector, never per request:

| Treatment | Behaviour |
|---|---|
| `include` | Verbatim. Band A and B records about the subject alone |
| `describe` | The fact without the other person: "You granted a business-domain entitlement to another user on 3 March" - Band C |
| `exclude` | Not collected at all. Security-sensitive rows: `secret_references`, `security_policies` values, `role_permissions` |

`describe` is the answer to Band C, and it is a default that a reviewer may
narrow but **never widen** without a second approval.

#### How security-sensitive information is redacted

`secret_references` and `security_policies` are `exclude`. The subject learns
they own a secret reference only as a count, never a pointer. Gate 3 established
that the credential map is a targeting list (SEC-DEC-052); an access request
must not be a way around that.

#### How raw audit data is handled

**Never released raw.** `audit_events` is collected as a rendered summary -
timestamp, action, outcome - with `before_summary` / `after_summary` **excluded
by default** because they can describe another person's record, and
`ip_address` excluded unless the reviewer justifies it. A reviewer may include a
specific event; they cannot include the table.

#### How response packages are produced

Rendered HTML review page inside SemantIQ, reviewed and approved, and the
response DELIVERED OUTSIDE the application - the register stores an evidence
reference to how it was sent. **No file is generated and no file is stored** in
gate 4. See decision D9; this is what avoids `public/storage`, a mail transport,
and a durable file full of personal data.

#### How corrections are approved and how they meet append-only history

- A correction to `users` is applied through the existing `UserRegistry`, so it
  is audited exactly like an administrator's edit, and the tenancy guard applies.
- **`audit_events` is never edited.** Where the subject asserts the trail is
  wrong, the outcome is a `privacy_correction_note` - a NEW append-only row
  linked to the event id, recording the assertion and the decision. The original
  event is untouched, and anyone reading it sees the annotation beside it.
- A correction that is refused records the reason. Refusal is a lawful outcome.

### 2.6 PDPA-02 Data Breach Assessment and Notification

**Screens:** Breach Register, incident detail.
**Routes:** `/admin/data-protection/breaches`, `/new`, `/{incident}`, POST for
assess, decide, record notification, close.

```text
detected -> contained -> assessing -> decided -> notifying -> closed
                                   \-> not_notifiable -> closed
```

Fields exactly as the product owner listed, plus:

| Field | Note |
|---|---|
| `reference` | `BR-0001`, quotable in correspondence |
| `pdpc_notification_due_at` | **Computed** from `assessment_completed_at` plus the profile's `pdpc_notification_due_days`. Stored on decision so the deadline that applied is preserved even if policy later changes |
| `deadline_basis` | The text from the profile at the moment of decision. Traceability, not a constant |
| `individuals_affected_estimate` | Integer, nullable, with an `estimate_basis` note |
| `data_categories_affected` | Links to `personal_data_categories` |

**Deadlines and reminders.** The due date is COMPUTED ON READ from stored
timestamps - no background job, no scheduler dependency. The register sorts by
urgency and shows overdue prominently. **Active notification - email, push -
needs a transport and a worker and is NOT in this gate.** Decision D10.

**The register is itself sensitive.** It names systems, weaknesses and affected
people. Its permission sits high; see 4.

### 2.7 PDPA-03 Per-category Retention Policy

**Screen:** Retention, under Data Protection.
**Routes:** `GET/PUT /admin/data-protection/retention`, POST approve.

Categories seeded from `config/governance.php`, covering the ten the product
owner named plus the two gate 4 introduces:

```text
audit_events, access_review_evidence, active_user_identity,
former_user_identity, network_identifiers, integration_logs,
security_events, configuration_history, privacy_request_records,
breach_records, sovereignty_exception_records, personal_data_category_registry
```

Each policy row: category, retention period, **basis**, retention start event
(`record_created` / `subject_departed` / `request_closed` / `incident_closed`),
disposal action (`delete` / `anonymise` / `retain_indefinitely`), anonymisation
option, owner, approval status, exception rule, next review date.

**The `audit_events` category is special and the screen says so.** Its disposal
action may be set, but a note on the row states that `audit_events` carries
`BEFORE UPDATE` and `BEFORE DELETE` triggers, that no application path can
delete from it, and that any sweep must drop, delete and recreate the triggers
as a separately approved operation (SEC-DEC-038, SEC-DEC-039). **No code in
gate 4 deletes anything.**

### 2.8 Required structured Privacy Contact

Four new columns on `organisations`:
`privacy_contact_name`, `privacy_contact_email`,
`privacy_contact_phone` (nullable), `privacy_contact_role` (nullable).

The existing single `privacy_contact` free-text column is **kept, not dropped**,
and the migration copies it into `privacy_contact_name` where it is not blank.
Dropping a column in the same release that adds its replacement leaves no way
back if the copy is wrong.

**Validation, staged so nothing breaks:**

| When | Behaviour |
|---|---|
| Migration | Backfill from the old column. Nothing is required yet |
| ADM-002 screen | Name and email required **on save**, so any organisation edited from now on is corrected |
| ADM-014 approval | A data protection profile **cannot be approved** without a complete privacy contact. This is the real gate |
| Security / Governance overview | A missing contact is a configuration gap, named and linked |

Existing organisations are never broken: nothing fails until somebody saves the
profile or the organisation, and both tell them exactly what is missing.

Changes are audited as `governance.privacy_contact.updated` with before/after -
key names checked against the redactor, see 4.4.

## 3. Database model

Seven new tables, one altered. Every one answered against the checklist.

### 3.1 Common decisions, applied to all seven

| Question | Answer |
|---|---|
| Organisation scoping | Every table carries `organisation_id`, NOT NULL, and uses `BelongsToOrganisation` |
| Global scope behaviour | Fails closed. No context, no rows |
| Null organisation | **Not permitted on any gate 4 table.** Unlike `system_settings` there is no platform-wide default worth having: a data protection profile belongs to a customer or it belongs to nobody |
| Deletion behaviour | `cascadeOnDelete` from `organisations`. User FKs are `nullOnDelete` so a record survives the person |
| Audit | Every write on every table |
| Readiness before migration | All seven behind `GovernanceStorage`; see 5 |

### 3.2 `data_protection_profiles`

Versioned, append-a-version. `status` in `draft` / `active` / `superseded`.
Unique partial index on `(organisation_id)` where `status = 'active'` - MySQL
has no partial index, so this is enforced by the service plus a unique index on
`(organisation_id, status, effective_from)`. Immutable once `active`.
Classification: Internal. Retention category: `configuration_history`.

### 3.3 `data_sovereignty_profiles`

Same shape and same versioning. Region lists as JSON arrays, validated against
`config/governance.php` region catalogue. Classification: Internal.
Retention: `configuration_history`.

### 3.4 `personal_data_categories`

The register ADM-014 needs and the thing PDPA-03 and PDPA-02 both point at.
Columns: `code`, `name`, `description`, `classification`, `is_special_category`,
`lawful_basis`, `retention_category`, `source_tables` (JSON, documentary),
`owner_user_id`, `status`. Seeded from the schema re-scan in 2.5.
Classification: Internal. Retention: `personal_data_category_registry`.

### 3.5 `retention_policies`

One row per category per organisation. Unique `(organisation_id, category)`.
Mutable, with every change audited - a retention policy is a living decision,
unlike a profile version. Classification: Internal.
Retention: `configuration_history`.

### 3.6 `sovereignty_exceptions`

Mutable through its workflow, immutable after `approved` except for revocation.
Unique `(organisation_id, reference)`. Indexes on `(organisation_id, status)`
and `(organisation_id, expires_on)`. Classification: Internal.
Retention: `sovereignty_exception_records`.

### 3.7 `privacy_requests` and `privacy_request_records`

`privacy_requests`: reference, `subject_user_id` (nullable - a requester may not
have an account), `subject_name`, `subject_email`, type, status, received_on,
due_on, `assigned_to_user_id`, identity verification status and evidence
reference, scope note, decision, decision reason, responded_on, closed_on,
response evidence reference.

`privacy_request_records`: the assembled scope. `privacy_request_id`, `band`,
`collector`, `source_table`, `record_reference`, `treatment`
(`include`/`describe`/`exclude`), `reviewer_decision`, `reviewer_user_id`,
`summary` (the rendered, treated text - never the raw row).

**Both contain personal data about the subject, and `privacy_request_records`
contains treated extracts of it.** Classification: **Restricted**.
Retention: `privacy_request_records`. **In scope for PDPA-01 itself** - see 3.10.

`privacy_correction_notes`: append-only annotations against `audit_events`.
Columns: `audit_event_id`, `privacy_request_id`, `assertion`, `decision`,
`decided_by_user_id`, `decided_at`. **No update path; model hooks throw**, the
same pattern as `AuditEvent`. **No database trigger** - see decision D11.

### 3.8 `breach_incidents`

Reference, detected_at, `owner_user_id`, systems affected, data categories
affected (JSON of `personal_data_categories.code`), individuals estimate and
basis, containment status, assessment_started_at, assessment_completed_at,
notifiable decision, decision reason, `pdpc_notification_due_at`,
`deadline_basis`, pdpc required/notified_at, individual required/notified_at,
evidence reference, status.

Classification: **Restricted**. It names weaknesses and affected people.
Retention: `breach_records`.

### 3.9 `organisations` - altered

Four columns added, nullable. `privacy_contact` retained. No index needed.

**One more index this gate needs, on an existing table:** `audit_events` has
four indexes and none supports the ADM-013 filter combination
`(organisation_id, occurred_at)` plus `outcome` or `module`. A composite
`(organisation_id, module, occurred_at)` and `(organisation_id, outcome,
occurred_at)` are proposed. **Adding an index to `audit_events` does not touch
its triggers** - triggers bind to the table, not to its indexes - but the
migration will state that explicitly so nobody assumes otherwise.

### 3.10 The recursion nobody should miss

**Gate 4 introduces personal data that is itself in scope for PDPA-01.**

| New table | Personal data it holds |
|---|---|
| `privacy_requests` | subject name, email, identity verification evidence |
| `privacy_request_records` | treated extracts of the subject's own data |
| `privacy_correction_notes` | the subject's assertion, in their words |
| `breach_incidents` | `owner_user_id`, and affected individuals by implication |
| all seven | `*_by_user_id` attribution, Band C |

The collector catalogue must include them, and the structural test in 2.5 will
fail if it does not. Stated here because it is the kind of thing a plan can
easily leave out and a regulator will not.

## 4. Permissions and audit model

### 4.1 New permissions

| Key | Ceiling | Auto-grant | Risk | Audited |
|---|---|---|---|---|
| `admin.audit.view` | **Domain Owner** (lowered - decision D2) | System Administrator | Normal | No |
| `admin.audit.view_network` | System Administrator | System Administrator | Elevated | No |
| `admin.data_protection.view` | Domain Owner | Admin | Normal | No |
| `admin.data_protection.manage` | Admin | System Administrator | High | Yes |
| `admin.data_protection.approve` | System Administrator | System Administrator | High | Yes |
| `admin.retention.view` | Domain Owner | Admin | Normal | No |
| `admin.retention.manage` | Admin | System Administrator | High | Yes |
| `admin.sovereignty.view` | Domain Owner | Admin | Normal | No |
| `admin.sovereignty.manage` | Admin | System Administrator | High | Yes |
| `admin.sovereignty.approve` | System Administrator | System Administrator | High | Yes |
| `admin.sovereignty_exceptions.view` | Domain Owner | Admin | Normal | No |
| `admin.sovereignty_exceptions.request` | Admin | Admin | Elevated | Yes |
| `admin.sovereignty_exceptions.approve` | System Administrator | System Administrator | High | Yes |
| `admin.privacy_requests.view` | Admin | System Administrator | Elevated | No |
| `admin.privacy_requests.manage` | Admin | System Administrator | High | Yes |
| `admin.privacy_requests.release` | System Administrator | System Administrator | High | Yes |
| `admin.breaches.view` | Admin | System Administrator | Elevated | No |
| `admin.breaches.manage` | Admin | System Administrator | High | Yes |

**Manage and approve are always separate.** A person who can weaken a
sovereignty profile should not be the person who blesses it.

**None names a business domain.** The gate 2 rule holds: a Domain Owner who can
read the audit log still holds no Finance data.

### 4.2 The Auditor problem - decision D2

`admin.audit.view` is declared at System Administrator today, the rail's Audit
Logs leaf sits under the `compliance` policy (Domain Owner or Auditor), and
`ROLE_MODEL.md` says an Auditor reads the audit trail. **Three sources, three
answers.** `NavigationIntegrityTest` will fail the moment the route exists.

The permission layer has **no Auditor concept at all** - `is_auditor` is
understood by `Navigation` and not by `Authorization`. So this is not a
one-line fix. Three options in decision D2.

### 4.3 Audit actions introduced


## 5. Deployment and migration safety model

### 5.1 The rule, restated

The deploy ships code and does not run migrations. Gate 3 proved what happens
when request-path code reads a table that does not exist yet: `GET /sign-in`
returned 500 and the whole site was down.

### 5.2 Which gate 4 code is on the request path

| Code | On every request? | Readiness needed |
|---|---|---|
| The seven screens | No - only under `/admin` | Yes, but a 500 there is contained |
| **The privacy contact on ADM-002** | No | Reads `organisations`, an existing table. Safe |
| **`config/governance.php` catalogue** | Read on demand only | No table. Safe |
| **Nothing in gate 4 runs on the web middleware stack** | - | **This is the key difference from gate 3** |

**Gate 4 adds no middleware.** No `SecurityHeaders` equivalent. That removes
the whole-site risk - but it does not remove the per-screen risk, and a 500 on
the Compliance cluster during a deployment window is still a defect.

### 5.3 `GovernanceStorage`

Same shape as `SecurityStorage`: `Schema::hasTable()` per table, memoised,
registered as a singleton, **never a caught database exception**.

| Path | Behaviour before migration |
|---|---|
| Profile READ | Falls back to the `config/governance.php` **safe defaults** - cross-border all false, Singapore, PDPA. A secure default state IS meaningful here |
| Retention READ | Falls back to the catalogue categories with no periods set, shown as Not Configured |
| **Privacy request READ** | **No fallback. There is no meaningful default for "somebody's access request".** The screen reports Migration Required |
| **Breach register READ** | Same. No default |
| Audit log READ | `audit_events` already exists. Unaffected |
| **All WRITES** | **Fail closed**, `GovernanceStorageNotInitialised`, nothing written, nothing audited as though it might have been |

The distinction matters: a profile has a meaningful secure default, a register of
real events does not, and inventing an empty register would be exactly the false
state gate 3's SEC-DEC-059 forbids.

### 5.4 Migration strategy

Eleven migrations, ordered so each is independently reversible:

```text
1  create_personal_data_categories_table
2  create_data_protection_profiles_table
3  create_data_sovereignty_profiles_table
4  create_retention_policies_table
5  create_sovereignty_exceptions_table
6  create_privacy_requests_table
7  create_privacy_request_records_table
8  create_privacy_correction_notes_table
9  create_breach_incidents_table
10 add_structured_privacy_contact_to_organisations_table
11 add_audit_log_filter_indexes_to_audit_events_table
```

Every one has a working `down()`. Migration 10 backfills; its `down()` drops
only the four new columns and leaves the original `privacy_contact` intact.
Migration 11 adds indexes only - **no data change, and the `audit_events`
triggers are untouched**, which the migration comment states explicitly so no
future reader assumes SEC-DEC-039 applies.

**No seeder migration.** The sovereignty draft profile and the retention
category rows are created on first visit to their screen by the service, not by
a migration, so a rollback cannot orphan them and re-running cannot duplicate
them.

### 5.5 Rollback and forward-fix

Rollback of gate 4 drops seven tables and four columns, and cannot damage gates
1 to 3 - no existing table is altered destructively.

**But the day note's standing guidance applies:** do not roll back on
production. `--step` counts migrations, not gates, and gate 4 is eleven
migrations sitting directly on top of gate 3's two. A `--step` intended for
gate 4 that is one too large starts eating gate 3.

Forward-fix is the default for anything found after merge.

## 7. Decisions requiring approval

Thirteen. The first four change the shape of the gate.

### D1 - Where do PDPA-01 and PDPA-02 live in the menu? SHAPE

`doc/MENU_STRUCTURE.md` has homes for ADM-013 to ADM-016 under Compliance. It
has **no home for Privacy Requests or a Breach Register.** Same situation as
DEC-001's gap M1 in gate 3.

**Proposed:** two new leaves under Data Protection, and a decision record DEC-003.

```text
Compliance

    |-- Data Protection Profile      ADM-014   (exists)
    |-- Personal / Sensitive Data    ADM-014   (exists, becomes the category register)
    |-- Privacy Requests             PDPA-01   <- NEW
    |-- Breach Register              PDPA-02   <- NEW
    |-- Retention                    PDPA-03   (exists)
    `-- ...unchanged leaves stay unbuilt
```

**Approve, amend, or name a different home.**

### D2 - Can an Auditor read the audit log? SHAPE

`ROLE_MODEL.md` says yes. `PermissionRegistry` says System Administrator only.
The rail says Domain Owner or Auditor. The permission layer has no Auditor
concept.

| Option | Consequence |
|---|---|
| **(a) Teach `Authorization` an auditor capability** - a permission may declare `orAuditor: true` | Honours ROLE_MODEL. Touches gate 2's authorization core, which is the most security-critical code in the application |
| (b) Lower `admin.audit.view` to Domain Owner, no auditor concept | Simple. An Auditor who is only an Auditor still cannot read the trail, so ROLE_MODEL stays unmet |
| (c) Keep System Administrator, correct ROLE_MODEL and the rail | Simplest and most honest about what exists. Narrows the Auditor role to almost nothing |

**Recommendation: (a).** ROLE_MODEL is the authorization authority, the Auditor
role exists precisely for this, and CLAUDE.md is explicit that hiding a menu item
is never authorization. It is the largest change, and I will not touch that code
without your word.

### D3 - Is there a Governance Overview screen? SHAPE

Gate 3 built a Security Overview under decision D5 and it has proved the most
useful screen in the group. Gate 4 has nine screens and no roll-up.

**Proposed:** one read-only Governance Overview: profile states, retention
coverage, open privacy requests against their due dates, open breaches against
theirs, active exceptions and what expires soon, and the configuration gaps.
No new policy, no new control.

**Approve or decline.** Declining is reasonable - it is a tenth screen.

### D4 - Are profiles versioned or editable? SHAPE

**Proposed: versioned.** An approved profile is immutable; changing it writes a
new version and supersedes the old. The alternative is a mutable row, which is
simpler and cannot answer "what was in force in March".

**Approve, or accept mutable rows and lose the point-in-time answer.**

### D5 - How much Band C attribution goes into an access response?

"Alice granted Bob the Finance entitlement" is personal data about both.

**Proposed:** `describe` by default - the action and date without the other
person's identity - with a reviewer able to narrow but never widen without a
second approval.

**Approve, or set a different default.** This is a legal judgement as much as a
technical one and may be worth putting to whoever owns compliance.

### D6 - Do subjects without a SemantIQ account get requests?

A contractor whose account was deleted still has personal data in
`audit_events`. **Proposed: yes** - `subject_user_id` is nullable and the
request carries name and email, with identity verification doing the work.

### D7 - The PDPC deadline: configurable, with what default and basis?

**Proposed:** 3 calendar days, stored as `pdpc_notification_due_days` on the
profile with a free-text `basis` field defaulting to a reference to Part VIB of
the PDPA. Computed at decision time and frozen on the incident.

**Confirm 3 days is right, and confirm the basis text with whoever owns
compliance.** I can state the field; I should not be the source of the legal
figure.

### D8 - Who may see `audit_events.ip_address`?

**Proposed:** a separate `admin.audit.view_network` permission at System
Administrator. An IP is personal data and is rarely needed.

### D9 - Is there any export, and does anything produce a file?

**Proposed: NO export and NO generated file in gate 4.** Responses are reviewed
on screen and delivered outside the application, with an evidence reference
recorded.

This avoids three unapproved dependencies at once: `public/storage` (not
linked), a mail transport (`MAIL_MAILER=log`), and a durable file full of
personal data with its own retention and access problem.

**If you want export, it is a separate approval** and brings all three
dependencies with it.

### D10 - Reminders and escalation for breach deadlines

**Proposed for gate 4:** computed on read, sorted by urgency, overdue shown
prominently. **No background job.**

Active reminders need `QUEUE_CONNECTION` other than `sync`, a running worker and
a mail transport - none approved. **Flagged as a gate 6 dependency**, not
smuggled in here.

### D11 - Does `privacy_correction_notes` get database triggers?

`audit_events` has `BEFORE UPDATE` / `BEFORE DELETE` triggers because model
hooks do not fire on a mass delete (SEC-DEC-021, SEC-DEC-037).
`privacy_correction_notes` is append-only for the same reason.

**Proposed: model hooks only in gate 4, and the triggers recorded as an
outstanding production step** - the same shape as `audit_events`, which took a
manual application. Triggers cannot go in a migration for the reason SEC-DEC-037
gives.

**Approve, or ask for the trigger statements up front so they go on with the
release.**

### D12 - Does the sovereignty profile seed itself from known production state?

**Proposed: yes, as a DRAFT** carrying Singapore / Singapore / none and citing
SEC-DEC-036. It is not approved until a person approves it.

### D13 - Does gate 4 lower any tier so a Domain Owner can operate governance?

The permission table in 4.1 puts read at Domain Owner and change at Admin or
System Administrator. That is a widening relative to gate 3, where everything
sat at System Administrator.

**Approve the split, or keep everything at System Administrator for now.**
