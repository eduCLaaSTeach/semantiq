# R1.4c-i invariants

PDPA-01 Privacy Requests. Written before the audit-evidence fix, not after it,
so that the invariants drive the code rather than describing whatever the code
already happened to do.

## How to read this

An invariant is a statement that must be true of the system no matter what
anybody types, clicks or posts. Each one below carries four things, because a
claim without all four is not checkable:

| Column | What it means |
| --- | --- |
| Enforcement | The one place that actually refuses. Not the screen, unless the invariant is about the screen |
| Negative test | A test that drives the FORBIDDEN thing and proves it was refused. A test that only exercises the happy path proves nothing about an invariant |
| Bypass result | What happens to a typed URL or a direct service call that skips the screen. Blank where the invariant is not reachable that way |
| Failure-state proof | What the database is asserted to hold AFTER the refusal. An exception being thrown is not proof that nothing was written |

## The public mutator rule

**Every public governance mutator must independently establish, for itself:**

1. who is acting;
2. whether that actor is authorized;
3. whether any required second approver is authorized;
4. whether the audit identity matches the decision identity;
5. whether failure leaves the database unchanged.

**A controller, a route middleware or a hidden screen is not accepted as the
only enforcement layer.** A method that is public is callable, and the next
caller may be a console command, a queued job, a future controller written by
somebody who did not read this file, or a test. Each of those bypasses every
layer above the service.

Point 4 is the one that hides best. A method taking a `User $reviewer` argument
while the audit trail derives its actor from `Auth::user()` has two identities
that nothing forces to agree: the decision can be evaluated as Alice and
recorded as Charlie, and both halves look correct in isolation. A comment
saying they are the same person is not an invariant - it is a hope.

Point 3 hides nearly as well, and it hides in two layers. "A second person" and
"a second person who is allowed to decide this" are different rules, and the
first is satisfied by any account at all, including a Viewer. But **the second
is not enough either.**

## Identity, authority, participation, evidence

For every approval control, prove all four separately:

| | Question | What proves it |
| --- | --- | --- |
| 1 | **Identity** - who is this person? | An authenticated session, not an argument |
| 2 | **Authority** - are they allowed to approve? | `Authorization::allows()` |
| 3 | **Participation** - did that person actually perform the approval? | An action they themselves took, while authenticated as themselves |
| 4 | **Evidence** - is their approval permanently recorded? | An audit event written in the same transaction |

**A user id supplied by somebody else proves neither participation nor
consent.** It is a claim about a person, made by a different person, and the
audit trail would faithfully record the claim as though it were the act.

This is the trap `retreat()` fell into. It checked identity and authority for
the second approver and recorded them as having approved. They had done
nothing: they never authenticated, never performed an approval action, never
saw the decision. A reviewer could have named any System Administrator in the
organisation and the trail would have said that person agreed.

The fourth column is the one this batch kept getting wrong. Two release
blockers in a row - the lifecycle atomicity defect and the audit-evidence
defect below - both passed a test suite that asserted an exception was thrown
and never looked at the row afterwards.

## The twelve invariants

### 1. Nothing is collected before identity verification

| | |
| --- | --- |
| Enforcement | `PrivacyRequests::assemble()` refuses an unverified subject; `moveTo()` independently refuses to enter a collecting state, via `PrivacyRequestStatus::permitsCollection()`. Two checks, deliberately, on the most dangerous operation in the gate |
| Negative test | `nothing_is_collected_before_identity_is_verified`, `no_records_exist_for_an_unverified_request` |
| Bypass result | The assemble route carries `permission:admin.privacy_requests.manage`; the service refuses regardless of how it is called |
| Failure-state proof | `privacy_request_records` is asserted empty for the request |

The failure mode is handing a stranger somebody else's personal data, which is
why one check was not judged enough.

### 2. Lifecycle legality is validated before persistent side effects

| | |
| --- | --- |
| Enforcement | `PrivacyRequests::assertCanMoveTo()`, non-mutating, called at the top of all six lifecycle methods before anything is written |
| Negative test | `an_illegal_release_leaves_no_release_evidence_behind`, `an_illegal_refusal_...`, `an_illegal_close_...`, `an_illegal_review_...`, `an_illegal_assembly_...`, `an_illegal_verification_...` |
| Bypass result | `a_typed_post_against_a_closed_request_leaves_nothing_behind` |
| Failure-state proof | Every business field re-read from the database and compared to its value before the attempt, plus an audit-event count per action |

### 3. Lifecycle operations are transactional

| | |
| --- | --- |
| Enforcement | `PrivacyRequests::atomically()` wraps each complete operation in `DB::transaction()`; `CorrectionNotes::record()` likewise |
| Negative test | The invariant-2 tests all pass through it, and the invariant-5 tests below prove a rollback of a mid-operation failure rather than of a pre-flight refusal |
| Bypass result | Not reachable by request shape |
| Failure-state proof | Same as 5 |

Validating earlier is deliberately not the whole fix. Moving the status change
to the top would leave a request in `responded` with no `released_at` if a
later write failed - the same contradiction pointing the other way. Only the
transaction removes the class of defect rather than one member of it.

### 4. A failed lifecycle action leaves business data AND required audit evidence unchanged

| | |
| --- | --- |
| Enforcement | Invariants 2, 3 and 5 together. There is no single line that enforces this one; that is why it is stated separately |
| Negative test | The whole of `LifecycleAtomicityTest` and `AuditEvidenceRollbackTest` |
| Bypass result | `a_typed_post_against_a_closed_request_leaves_nothing_behind` |
| Failure-state proof | Field-by-field comparison plus `AuditEvent` counts per action, before and after |

### 5. A required PDPA audit failure rolls back the lifecycle action

**This is the invariant that was false, and the blocker this document was
written for.**

`AuditLogger::record()` catches its own write exception, logs it and returns
`null`. That is correct and deliberate for gate 1: a full disk must not stop an
administrator disabling a compromised account. But it made the invariant above
untrue for PDPA-01, because a release could commit its business fields and its
status change with the audit INSERT silently missing - a disclosure recorded as
having happened, with no evidence that it did.

| | |
| --- | --- |
| Enforcement | `AuditLogger::recordRequired()` throws `RequiredAuditEvidenceMissing` when `record()` returns null. Called inside the transaction, so the throw rolls the whole operation back. Used by the seven PDPA-01 lifecycle events and the three correction-note events, and nowhere else |
| Negative test | `AuditEvidenceRollbackTest`, ten tests: `a_failed_audit_on_receive_leaves_no_privacy_request_row`, `..._on_verify_leaves_the_verification_fields_and_status_unchanged`, `..._on_assemble_leaves_no_records_no_timestamp_and_no_status_change`, `..._on_review_leaves_the_review_fields_unchanged`, `..._on_release_leaves_no_release_fields_and_no_status_change`, `..._on_refusal_leaves_no_decision`, `..._on_close_does_not_close_the_request`, `..._on_a_correction_note_leaves_no_note`. The failure is forced by a listener that throws on `AuditEvent` creation, so the REAL `AuditLogger` catch block runs and returns the REAL null - a fake logger would prove only that the fake works. **Proved against the defect: 9 of the 10 fail without `recordRequired()`.** The tenth, `an_ordinary_administrative_action_still_succeeds_when_the_audit_write_fails`, passes either way on purpose - it guards the gate 1 behaviour against being broadened by this change |
| Bypass result | `a_typed_release_post_rolls_back_when_the_audit_write_fails` |
| Failure-state proof | The request row, its fields, its assembled records and its status are all re-read from the database and asserted unchanged - or, for `receive`, asserted not to exist at all |

Ordinary audit writes elsewhere remain best-effort. The rule is not broadened
to other modules, because the reason it applies here is specific: a disclosure
or refusal record whose required evidence is missing is internally
inconsistent, and this table exists to be evidence. SEC-DEC-089.

### 6. The reviewer is not the releaser

| | |
| --- | --- |
| Enforcement | `PrivacyRequest::releaseBlockedBecause()`, consulted by `PrivacyRequests::release()` |
| Negative test | `the_reviewer_cannot_also_release`, `a_response_cannot_be_released_before_it_is_reviewed` |
| Bypass result | `a_typed_post_cannot_bypass_the_separation_of_duties` |
| Failure-state proof | `released_at`, `released_by_user_id` and `evidence_reference` asserted still null |

The permission split was never sufficient on its own: a System Administrator
holds both `.manage` and `.release`, so two permissions held by one person are
one person.

### 7. The assembler is not the releaser

| | |
| --- | --- |
| Enforcement | Same method, using `assembled_by_user_id` - recorded so the rule binds to the person who did the work rather than to a tier |
| Negative test | `the_assembler_cannot_release_even_when_somebody_else_reviewed` |
| Bypass result | Covered by the same typed-post test |
| Failure-state proof | Same fields asserted still null; `who_assembled_the_response_is_recorded` proves the column is actually populated, so the rule has something to bind to |

### 8. Band C never exposes another person's identity

| | |
| --- | --- |
| Enforcement | Structural, not a rule about rendering. `AttributionCollector` selects a COUNT and a date range, joins to no user and never loads the other party, so the rendering function is given nothing it could leak. `CollectedItem` refuses a `describe` or `exclude` item carrying a payload, at construction |
| Negative test | `another_persons_identity_never_appears_in_an_assembled_response`, `band_c_items_are_described_and_carry_no_payload`, `a_described_item_cannot_carry_a_payload`, `widening_a_band_c_item_still_discloses_no_payload` |
| Bypass result | Widening the treatment is the bypass a reviewer has; the last test proves it still discloses no payload |
| Failure-state proof | Asserted against the rendered summary AND the JSON detail column |

### 9. The audit trail never stores assembled personal-data payloads

| | |
| --- | --- |
| Enforcement | `PrivacyRequests::summarise()` emits reference, type, status, whether the subject has an account, and the received date. The assembly event records an item COUNT. Every column name in the three tables was checked against `Redaction::isSensitiveKey()` |
| Negative test | `the_audit_trail_records_that_an_assembly_happened_and_never_what_was_in_it`. **Proved against a deliberate leak probe**: the subject's name was added to `summarise()`, the test was confirmed to name the offending event, the probe removed |
| Bypass result | Not reachable by request shape |
| Failure-state proof | Every audit row for the request is read back and asserted not to contain the subject's name, email, or any assembled summary or detail text |

### 10. No export, file, mail, queue or scheduler path exists

| | |
| --- | --- |
| Enforcement | Absence. There is no controller action, route or service method that produces one. Decisions D9 and D10 |
| Negative test | `assembling_writes_no_file_queues_no_job_and_sends_no_mail`, `no_deletion_or_export_path_exists` |
| Bypass result | The route list itself is asserted |
| Failure-state proof | Mail, Bus and Storage fakes asserted empty after a full assembly |

An invariant of absence needs a test more than most, because nothing in the
code will remind anybody it was a decision.

### 11. Correction notes remain append-only

| | |
| --- | --- |
| Enforcement | Two MySQL triggers, `BEFORE UPDATE` and `BEFORE DELETE`. The model hooks are defence in depth and are explicitly NOT the control - they do not fire on a mass delete or a raw query, and MySQL has no DENY |
| Negative test | `a_correction_note_cannot_be_updated`, `a_correction_note_cannot_be_deleted`, `a_raw_update_is_refused_by_the_database`, `a_raw_delete_is_refused_by_the_database`, `a_mass_delete_is_refused_and_the_row_survives` |
| Bypass result | The raw-query tests ARE the bypass case |
| Failure-state proof | The row is re-read and compared field by field after each refusal |
| Outstanding | The triggers are a separately approved production step, not a migration - a migration that can create a trigger can also drop it. R1.4c-i is not accepted until both exist on production and their definitions match the approved SQL. SEC-DEC-066 |

### 12. Any change to disclosure treatment is evidence-critical

**The treatment mutation and its audit evidence succeed together, or neither
succeeds.**

`PrivacySubjectAssembler::retreat()` decides what a privacy response is allowed
to disclose. Narrowing is one reviewer's call; widening can expose a person who
asked for nothing, and takes a second approver who is not the reviewer. All of
that was persisted - `treatment`, `reviewer_action`, `reviewer_note` - and none
of it produced an audit event. The second approval was enforced and then
forgotten: nothing in the trail said who agreed to disclose more, or why.

That the method is not yet reachable from any screen is not the point. It is a
public persistent write path, and **an unreachable user interface is not an
audit control** - the next screen that calls it inherits the gap silently.

| | |
| --- | --- |
| Enforcement | `retreat()` runs the record update and `AuditLogger::recordRequired()` inside one `DB::transaction()`. Everything below is asserted before any write |
| Negative test | `a_failed_audit_on_narrowing_leaves_the_treatment_unchanged`, `a_failed_audit_on_widening_leaves_the_treatment_unchanged` |
| Bypass result | Not reachable by request shape today. That is exactly why the control lives in the service and not in a screen |
| Failure-state proof | `treatment`, `reviewer_action` and `reviewer_note` are re-read from the database and the whole snapshot compared, and the `treatment_changed` event count is asserted to be zero |
| Disclosure-payload non-leak proof | `a_treatment_change_is_recorded_without_any_collected_personal_data` reads the audit row back and asserts it contains neither the item's `summary` nor its `detail`, nor the subject's name or email |

One action, `governance.privacy_request.treatment_changed`, with structured
before and after evidence - not one action per direction. The direction is a
field, because `narrowed` and `widened` are the same decision made two ways and
a reader filtering the trail wants both together.

### 12a. The reviewer is the authenticated actor

`retreat()` took a `User $reviewer` while `AuditLogger` derived its actor from
`Auth::user()`, and **nothing made them the same person.** A caller could pass
Alice as the reviewer while Charlie was signed in: the decision would be
evaluated against Alice's authority and the audit event attributed to Charlie,
each half correct on its own and the pair worthless. The code comment claiming
they were the same was a hope, not an invariant.

| | |
| --- | --- |
| Enforcement | `retreat()` refuses when `Auth::user()` is null, and refuses when its id differs from `$reviewer`. This is an interactive governance decision, so there is no legitimate caller acting on somebody else's behalf. `reviewer_user_id` is ALSO written into the audit evidence, so the identity is on the row explicitly rather than inferred from the actor column |
| Negative test | `a_reviewer_who_is_not_the_authenticated_actor_is_refused`, `an_unauthenticated_treatment_change_is_refused` |
| Failure-state proof | Full snapshot compared, `treatment_changed` count asserted zero |

### 12b. Widening is refused. Narrowing is allowed

**D5 is enforced fail closed.** A disclosure may be NARROWED now. WIDENING
requires an independently authenticated second approval, and that workflow does
not exist in this release, so widening is refused outright.

The previous implementation asked for a second approver, checked that they were
a different person, checked that they held `admin.privacy_requests.release`, and
recorded them in the audit trail as having approved. **They had not.** They were
a `User` object handed over by the reviewer. They never authenticated, never
performed an approval action and never saw the decision. Authorization answered
question 2 above and nothing answered question 3.

That is worse than having no second-approver rule at all, because the audit
trail would have carried a false statement - "this person approved" - in the one
record whose purpose is to show that two people were involved.

| | |
| --- | --- |
| Enforcement | `retreat()` refuses any change where `DisclosureTreatment::isWiderThan()` is true, with a message that says the workflow is not enabled rather than implying the caller did something wrong. **The `$approver` parameter is removed from the signature**: an argument that cannot mean what it appears to mean should not be accepted at all, and this API is unmerged, so there is no compatibility reason to keep it |
| Negative test | `widening_is_refused_because_no_approval_workflow_exists`, `widening_is_refused_even_when_the_reviewer_is_a_system_administrator`, `widening_is_refused_for_every_authority_level`, `the_api_cannot_express_a_second_approver` |
| Bypass result | None. There is no route, and the method's signature has no way to name an approver |
| Failure-state proof | Every refusal asserts the full row snapshot and a zero `treatment_changed` event count |

`the_api_cannot_express_a_second_approver` reads the method signature by
reflection and asserts no parameter is named for an approver. It is the
strongest available form of "a supplied System Administrator cannot widen": the
code cannot express the claim, so no future caller can accidentally revive it.

**The future workflow is NOT assigned to R1.4c-ii.** Its scope requires separate
approval. What is recorded here is only that widening is closed until it exists.

### 12c. Narrowing keeps every other control

Narrowing is one reviewer's call, and it is still a disclosure decision.

| | |
| --- | --- |
| Enforcement | `retreat()` requires an authenticated reviewer who IS the named reviewer and holds `admin.privacy_requests.manage`; runs the mutation and `recordRequired()` in one transaction; records `reviewer_user_id` |
| Negative test | `a_reviewer_who_is_not_the_authenticated_actor_is_refused`, `an_unauthenticated_treatment_change_is_refused`, `a_reviewer_without_manage_is_refused`, `a_failed_audit_on_narrowing_leaves_the_treatment_unchanged` |
| Failure-state proof | Full snapshot compared, event count asserted zero |
| Disclosure-payload non-leak proof | `a_treatment_change_is_recorded_without_any_collected_personal_data` |

**The reviewer is recorded as an id, not a name.** `reviewer_user_id` sits in the
structured evidence and matches the audit actor. An id resolves to a person for
anybody entitled to resolve it and discloses nothing to anybody who is not.

## What this document is not

It is not a test plan and not a substitute for the verification report. It is
the list of things that must stay true while the code around them changes, so
that the next person to touch this module can tell in one read whether they
have broken something that matters.

Anything added to PDPA-01 that is not covered by one of these twelve should
either map onto one of them or be added here as a thirteenth.
