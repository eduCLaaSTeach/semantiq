# Part 1. R1.4c-i - PDPA-01 Privacy Requests

The hardest feature in the gate. A person asks what personal data SemantIQ holds
about them, or asks for it to be corrected.

## 1.1 Proposed tables and columns

Three tables. All organisation-scoped, all following the gate 1 conventions.

### `privacy_requests`

The request itself, and its lifecycle.

| Column | Type | Null | Note |
| --- | --- | --- | --- |

| `status` | varchar(32) | no | The state machine below. Default `received` |
| `request_type` | varchar(16) | no | `access`, `correction`, `withdrawal` |

### `privacy_request_records`

One row per collected item. This is the assembled response, held as structured
rows rather than as a document, because **no file is produced** (D9).

| Column | Type | Null | Note |
| --- | --- | --- | --- |
| `id` | bigint unsigned PK | no | |
| `organisation_id` | FK, cascade | no | |
| `privacy_request_id` | FK privacy_requests, cascade | no | |
| `band` | varchar(1) | no | `A`, `B`, `C`, `D` |
| `source_table` | varchar(64) | no | Which table it came from |
| `collector` | varchar(190) | no | The collector class that produced it |
| `treatment` | varchar(16) | no | `include`, `describe`, `exclude` |
| `summary` | text | yes | What the subject is told. **Already rendered** |
| `detail` | json | yes | Structured payload, only for `include` |
| `occurred_at` | timestamp | yes | For time-ordered bands |
| `reviewer_action` | varchar(16) | yes | `kept`, `narrowed`, `widened` |
| `reviewer_note` | text | yes | **Required when widened** |
| `timestamps` | | | |

Index: `(organisation_id, privacy_request_id, band)`.

**Why store the assembled result at all?** Because a response must be
reproducible. If the answer were recomputed at read time it would change as the
underlying data changed, and nobody could say what was actually disclosed on the
day. The rows are the evidence of what was released.

| `outcome` | varchar(16) | no | `noted`, `applied`, `refused` |
| `outcome_reason` | text | no | Always required, including on `applied` |
| `decided_by_user_id` | FK users, nullOnDelete | yes | |
| `decided_at` | timestamp | yes | |
| `created_by_user_id` | FK users, nullOnDelete | yes | |

## 1.2 The complete state machine

```
                         +-----------------------------+
                         |          received           |
                         +--------------+--------------+
                                        | verify identity
                                        v
                         +-----------------------------+
                         |    identity_verification    |
                         +------+---------------+------+
                     verified   |               |  cannot verify
                                v               v
                   +-------------------+   +----------+
                   |    assembling     |   | refused  |
                   +---------+---------+   +----+-----+
                             | collection ran   |
                             v                  |
                   +-------------------+        |
                   |    in_review      |        |
                   +----+---------+----+        |
              access    |         |  correction |
                        |         v             |
                        |  +----------------+   |
                        |  |awaiting_decision|  |
                        |  +---+--------+---+   |
                        |      |        |       |
                        v      v        v       |
                   +-----------+   +---------+  |
                   | responded |   | refused |<-+
                   +-----+-----+   +----+----+
                         |              |
                         v              v
                      +---------------------+
                      |       closed        |
                      +---------------------+
```

**Transition rules, enforced in the service, not only in the UI:**

| From | To | Guard |
| --- | --- | --- |
| `received` | `identity_verification` | `admin.privacy_requests.manage` |
| `identity_verification` | `assembling` | Identity verified. **Hard gate: no collection runs before this** |
| `identity_verification` | `refused` | Reason required |
| `assembling` | `in_review` | Collection completed without error |
| `in_review` | `awaiting_decision` | Correction requests only |
| `in_review` | `responded` | Access requests. **`admin.privacy_requests.release`, re-authenticated** |
| `awaiting_decision` | `responded` / `refused` | Release permission; reason required on refusal |
| `responded` / `refused` | `closed` | Evidence reference recorded |

**Backward transitions are refused.** A closed request is reopened by raising a
new one, so the record of what was disclosed on a date cannot be edited later.

**Re-assembly.** `in_review` may return to `assembling` if a reviewer asks for a
re-run. That is a forward transition in intent and appends new record rows; it
never edits the previous ones.

## 1.4 Band treatments, and why each band has one

| Band | Definition | Default | Reviewer may narrow | Reviewer may widen |
| --- | --- | --- | --- | --- |
| **A** | The subject's own record | `include` | Yes, with note | Not applicable - already full |
| **B** | Records *about* the subject | `include`, rendered | Yes, with note | `audit_events` payloads and IP only, with note and second approval |
| **C** | The subject's name on somebody else's record | **`describe`** | Yes, to `exclude` | **Never without a second approval (D5)** |
| **D** | Free text that may name a person | Case by case, default `describe` | Yes | Never without a second approval |

**Band C is the whole design problem.** "Alice approved Bob's Finance
entitlement" is personal data about Alice *and* about Bob. Releasing it verbatim
to Alice discloses Bob, who did not ask for anything and did not consent.
Withholding it entirely under-answers a lawful request.

`describe` resolves it by disclosing **the fact without the second person**:
*"You granted a business-domain entitlement to another user on 3 March 2026."*
Alice learns what she did. Bob is not named.

## 1.5 How other-person disclosure is prevented

Four mechanisms, deliberately overlapping. Any one of them failing should not
release another person's identity.

1. **Treatment is decided per collector, never per request.** A reviewer under
   time pressure cannot accidentally widen a whole band; the default is in code
   and reviewed like code.
2. **Widening requires a second approval.** Narrowing is one person's call.
   Widening is the dangerous direction, so it is the direction that needs two
   people. Enforced in the service, and the second approver may not be the
   first.
3. **The `describe` renderer never receives the other person's identity.** It
   is given the date, the action and the resource type. The other party's name
   and id are not passed in, so a template mistake cannot leak what the function
   never held.
4. **A test asserts the negative.** For a fixture where Alice acted on Bob's
   record, the assembled response for Alice is asserted not to contain Bob's
   name, email or user id **anywhere in the rendered output**, including the
   JSON detail column.

## 1.6 Identity verification rules

**Nothing is collected before identity is verified.** The transition guard is in
the service; `assembling` is unreachable from `received`.

- Verification records **who** verified, **when**, by **what method**, and a
  note of what was actually checked.
- Method is a codified list in `config/governance.php`, not free text:
  `signed_in_session`, `government_id_sighted`, `employer_confirmation`,
  `registered_email_challenge`, `in_person`, `other_documented`.
- **A request may exist for a person with no SemantIQ account** (D6).
  `subject_user_id` is nullable. A contractor whose account was deleted still
  has personal data in `audit_events`, and the PDPA does not stop applying
  because the account did.
- **That is also the obvious attack**: assemble a stranger's data by asserting
  you are them. Verification carries the weight an authenticated session would
  otherwise carry, which is why it is mandatory and recorded rather than a
  checkbox.
- Failure to verify is a lawful outcome: transition to `refused` with a reason.

## 1.7 Correction notes and append-only history

**`audit_events` is never edited.** Where a subject asserts the trail is wrong,
the outcome is a new `privacy_correction_note` linked to the event id. The
original event is untouched and anyone reading it sees the annotation beside it.

**A correction to `users` is applied through the existing `UserRegistry`**, so
it is audited exactly like an administrator's edit and the tenancy guard
applies. No second write path.

**Application-level protections** (this batch):

- Model hooks on `saving` and `deleting` throw for any existing row.
- No `update()`, `delete()` or `destroy` route exists. A test scans method names
  and registered route verbs, in the shape of R1.4b's `no_deletion_path_exists`.
- `audit_event_id` uses `restrictOnDelete`, not cascade: an annotation must not
  disappear because something upstream was removed.

**Database protections** (SEC-DEC-066, a separate approved production step):

The model hooks are **defence in depth, not the control**. They do not fire on a
mass delete, and MySQL has no DENY so privileges cannot express this. The
triggers are authoritative, exactly as for `audit_events` (SEC-DEC-037).

**R1.4c-i is not accepted until these exist on production and are proved.**

## 1.8 Proposed production trigger SQL - DOCUMENTATION ONLY

**Not executed by this plan, not executed by any migration, and not executed by
me.** Presented for review now so the wording is agreed before it is ever run.

Triggers stay out of migrations for SEC-DEC-037's reason: a migration that can
create them can also drop them, which would make the protection removable by the
same mechanism that is supposed to install it.

```sql
-- Append-only protection for privacy_correction_notes. SEC-DEC-066.
-- Run as a separately approved production step, AFTER the R1.4c-i migration.
-- Requires TRIGGER privilege. Does not modify any row.

DELIMITER $$

CREATE TRIGGER privacy_correction_notes_no_update
BEFORE UPDATE ON privacy_correction_notes
FOR EACH ROW
BEGIN
    SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT =
        'privacy_correction_notes is append-only. A correction note records what a data subject disputed; it cannot be edited.';
END$$

CREATE TRIGGER privacy_correction_notes_no_delete
BEFORE DELETE ON privacy_correction_notes
FOR EACH ROW
BEGIN
    SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT =
        'privacy_correction_notes is append-only. A correction note records what a data subject disputed; it cannot be deleted.';
END$$

DELIMITER ;
```

**Both identifiers are under 64 characters** (34 and 34).

**Proof afterwards**, to be recorded in the verification document:

```sql
SELECT TRIGGER_NAME, EVENT_MANIPULATION, ACTION_TIMING
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE()
  AND EVENT_OBJECT_TABLE = 'privacy_correction_notes';
```

Expected: two rows, `BEFORE UPDATE` and `BEFORE DELETE`.

**On proving they FIRE rather than merely exist.** For `audit_events` the
product owner declined the DELETE-trigger proof and that instruction stands. The
same question arises here. **I propose the same posture: prove existence, do not
run a destructive proof against production.** The triggers are proved to fire in
the test suite against a real trigger installed in the test database, which is
how `AuditIndexMigrationTest` already works. If a live proof is wanted it is a
separate decision, and it needs a row that exists only to be attacked.

## 1.9 Permissions and re-authentication

Three new permissions. **Total moves 38 to 41.**

| Key | Ceiling | Auto-grant | Auditor | Risk | Re-auth | Audited |
| --- | --- | --- | --- | --- | --- | --- |
| `admin.privacy_requests.view` | Admin | System Administrator | **No** | Elevated | No | No |
| `admin.privacy_requests.manage` | Admin | System Administrator | **No** | High | Yes | Yes |
| `admin.privacy_requests.release` | System Administrator | System Administrator | **No** | High | **Yes** | Yes |

**None carries `orAuditor`.** An Auditor reads the audit trail. A privacy
request contains a named person's assembled personal data, which is a different
and larger thing. R1.4b's capability is not extended here.

**`release` is separate from `manage` on purpose.** Assembling a response and
deciding to disclose it are different acts. The person who ran the collection
should not be the only pair of eyes on what leaves the building.

**Second-approval rule for widening** is enforced in the service, not by a
permission: the widening approver must hold `release` **and** not be the person
who set the narrower treatment.

**Redactor check.** Every action key and every audit-summary key was run through

summaries carry the reference, the state change and the reason only.

## 1.11 Deployment-order behaviour with all three tables absent

## 1.13 Structural tests against schema drift

**The most valuable test in the gate**, and the reason the matrix in 1.3 is
exhaustive rather than illustrative:

```
every_schema_table_is_claimed_or_excluded_with_a_reason
```

It reads the live schema, and for each table asserts it is either claimed by a
registered collector or listed in the exclusion register **with a non-empty
reason**. A new table added by gate 5, 6 or 7 fails the build until somebody
decides which it is.

Proved against a deliberate drift probe, as `DataDocsTest` was: a fake table is
added, the test is confirmed to name it, the probe is removed.

Supporting tests:

| Test | Asserts |
| --- | --- |
| `no_collection_runs_before_identity_is_verified` | The state guard, at service level |

# Part 2. R1.4c-ii - Breach Register and Governance Overview

**Not started until R1.4c-i is accepted.** Outlined here so the shape is agreed;
detailed design is presented for approval before that batch begins.

## 2.1 PDPA-02 Breach Register

One table, `breach_incidents`. Two permissions: `admin.breaches.view` (Admin,
Elevated), `admin.breaches.manage` (Admin, High, audited). Neither carries
`orAuditor`.

```
detected -> contained -> assessing -> decided -> notifying -> closed
                                   \-> not_notifiable -> closed
```

**D7 preserved exactly.** The PDPC deadline is computed from the configured rule
in `config/governance.php` and **frozen onto the breach record at decision
time**, together with the basis text and the reference used. A later policy edit
cannot move a date somebody is being held to.

**Not built:** automatic PDPC notification, email, scheduler, reminder worker.
Deadlines are computed on read from stored timestamps. The register sorts by
urgency and shows overdue prominently, and that is the whole of the reminder
mechanism.

## 2.2 Governance Overview

Read-only. Nine values, each read from the feature that owns it: both profile
statuses, privacy contact, retention coverage, open privacy requests, open
breaches, active exceptions, expiring exceptions, configuration gaps.

**It creates no policy and no control of its own.** If the overview and a
feature screen can disagree, the overview is wrong by construction.

**The four conversions it must never make:**

```
Draft           -> Healthy      FORBIDDEN
0 tracked       -> Healthy      FORBIDDEN
Not Configured  -> Healthy      FORBIDDEN
Not Determined  -> Healthy      FORBIDDEN
```

Each is asserted by a test driving the real state. This is SEC-DEC-059 and
SEC-DEC-060 applied in full: both cost a follow-up PR in gate 3, and both were
found by the product owner on the live site rather than by the suite. The
summary sentence is calculated from the same memoised result as the badge, so
the two are incapable of contradicting each other.

# Part 4. Rollback and recovery

**R1.4c-i migrations are additive and independently reversible.** Each `down()`
drops only its own table, in reverse dependency order:
`privacy_correction_notes`, then `privacy_request_records`, then
`privacy_requests`.

**The triggers are not in a migration**, so a rollback cannot remove them. If
the tables are dropped while triggers exist, the triggers go with their table -
which is why the production procedure is: migrate first, install triggers
second, and prove them third.

**Forward-fix is preferred over rollback**, as in R1.4b. The R1.4b incident
showed that a failed migration leaves MySQL in a half-applied state that a
rollback cannot clean up either, and that a read-only pre-check plus a targeted
repair is the safer path.
