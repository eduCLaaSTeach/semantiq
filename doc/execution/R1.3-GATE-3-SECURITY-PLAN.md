# R1.3 - Gate 3, Security: implementation plan

**Release:** Administrator Foundation Release 1
**Gate:** 3 of 7
**Features:** ADM-009 Authentication Policy, ADM-010 Session Policy, ADM-011 API Security, ADM-012 Secret References
**Navigation home:** `doc/MENU_STRUCTURE.md` section 12.16, settled by DEC-001
**Status:** IMPLEMENTED. Decisions D1 to D5 approved by the product owner
25 August 2026; built in R1.3 and verified in
`doc/execution/ADMIN-FOUNDATION-RELEASE-1-VERIFICATION.md`, "Gate 3 - Security".

Two things changed during implementation, both recorded rather than done
silently:

- **D4 covers FOUR critical actions, not three.** The plan said three because
  it counted only what existed when the plan was written; ADM-012 secret
  references exist once this gate ships, and ADM-010 names a secret-reference
  change as a critical action. The principle you approved - only actions that
  exist today - is unchanged.
- **Deployment order was not in this plan at all, and it should have been.**
  Section 11 covered rolling the migrations back; it did not ask what happens
  between the code deploying and the migration running. Gate 3 middleware runs
  on the web stack, so the answer was a 500 on `/sign-in` - the whole site,
  not just the Security screens. Found in review of PR #21, fixed in the same
  PR, and written up as section 12 of the verification document, because it is
  a property of every future release that adds a table rather than a one-off.
- **The policy key namespace is shaped by the audit redactor.** `sign_in.`,
  `activity.` and `api.` rather than `auth.` and `session.`, because
  `Redaction` replaces the value of any key containing the latter two and a
  policy change would have been recorded as "[redacted]". Section 3 D1
  predicted the refusal on the way in; it did not predict that the same list
  would also shape what the keys could be called. SEC-DEC-044.

This document exists because the R1.3 section of
`doc/execution/ADMIN-FOUNDATION-RELEASE-1-PLAN.md` is two lines long. It names
four features and three tables and nothing else, and three of the four features
turn out to have prerequisites the repository does not currently meet. Those are
in section 3.

## 3. Architectural decisions required before coding

Five. Each one is a place where the release plan, the existing code, or the
production environment disagree with what the feature needs.

### D1 - Where authentication and session policy values are stored

**The release plan says** tables `security_policies` and `session_policies`.

**The existing code says** runtime configuration lives in `system_settings`,
typed by a catalogue in `config/platform.php`, written only through
`SystemSettings`, which is documented as "the only supported way in or out".

**The blocker that decides it.** `SystemSettings::set()` refuses any key that
`Redaction::isSensitiveKey()` matches. That list contains the fragments `auth`,
`session`, `key`, `token`, `secret`, `credential`, `cookie`, `private`, `cert`,
`nonce`, `salt` and `signature`. Every natural key for these two features trips
it:

```text
auth.mode                -> contains "auth"    -> REFUSED
session.idle_minutes     -> contains "session" -> REFUSED
security.session.max     -> contains "session" -> REFUSED
```

The same fragments also drive `Redaction::summarise()`, which is what writes the
audit before/after summary. Storing these under such names would make the audit
record of a policy change read `[redacted]` instead of "idle timeout 120 -> 30" -
degrading the trail for precisely the settings an auditor comes for.

Reusing `system_settings` therefore means naming every key to dodge a redaction
guard, and leaving a trap for the next person who adds `security.session_*` and
gets an inexplicable refusal.

**Proposed:** ONE new table `security_policies`, not two. A catalogue in
`config/security.php` modelled on the platform catalogue, and a
`SecurityPolicies` service with the same four guards as `SystemSettings` plus a
required change reason on high-risk keys.

**This deviates from the release plan's table list**, which named
`security_policies` AND `session_policies`. Splitting one key/value policy store
into two tables by subject matter buys nothing and doubles the machinery.
Recorded here rather than done silently.

**Rejected:** two parallel configuration systems; and contorted key names inside
`system_settings`.

### D2 - What ADM-011 API Security actually is

Release plan section: "No public API surface is added in this release." A screen
that configures the security of an API that does not exist would be four
settings nothing reads - the "unwanted parts hanging" problem by definition.

ADM-011's own text is a list of **controls**, not settings: authentication by
default, authorization per endpoint, CSRF, input validation, rate limiting,
correlation IDs, bounded payloads, structured errors, secure headers, no secrets
in errors.

**Proposed:** ADM-011 becomes a **verification screen backed by live checks**,
in the shape of the existing `HealthCheck` / Diagnostics pattern, plus the small
number of genuinely tunable values. It reports, from the running application:

| Control | How it is checked | Today |
|---|---|---|
| Authentication by default | Every route outside the guest group carries `auth` | Pass |
| Authorization per endpoint | Every `admin.*` route names a `policy` or `permission` | Pass |
| CSRF | The `web` group's `ValidateCsrfToken` is present and no route excludes it | Pass |
| Correlation IDs | `AssignCorrelationId` is prepended to the `web` group | Pass |
| Rate limiting | The credential path has a limiter, from policy | Pass |
| Secure headers | A response carries the six headers | **FAIL today - to be built** |
| Bounded payloads | A configured cap is enforced | **FAIL today - to be built** |
| No secrets in errors | `Redaction::scrub()` applied to outbound messages | Pass |

Two of the eight fail today. That is the point of the screen: it tells the truth
about the application rather than restating an intention.

**New middleware `SecurityHeaders`** ships with it, sending
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Permissions-Policy`, `Content-Security-Policy` and, when the request is HTTPS,
`Strict-Transport-Security`. HSTS is policy-switched and defaults OFF, because a
wrongly issued HSTS header cannot be withdrawn from a browser that cached it.

The tunable values move OUT of code and into policy: the sign-in attempt
threshold and lock duration currently sit as private constants in
`SignInController`, which means ADM-009's "Failed Login Threshold" and "Lock
Duration" cannot be set at all today.

### D3 - Session revocation cannot work on production as configured

ADM-010 requires Session Revocation and a Concurrent Session Policy. Both need
the application to enumerate a person's live sessions.

Production runs `SESSION_DRIVER=file`. File sessions are opaque blobs keyed by
session id with no index by user, so neither capability is possible there.
Laravel's own `logoutOtherDevices` is not an escape: it works by rehashing the
password, and a federated account has no password to rehash.

The `sessions` table already exists with a `user_id` column. The fix is
`SESSION_DRIVER=database` in the server `.env`.

**This is a production configuration change and needs your approval.** It also
signs everybody out at the moment it takes effect, because existing file
sessions are not migrated.

**Proposed, whatever you decide:** build the capability against the database
driver, and have the screen detect the running driver. On `file` it states
plainly that revocation is unavailable and why, and the action is absent rather
than present-and-broken. That way the feature is not hanging, and the
prerequisite is named on the screen instead of in a document.

### D4 - Re-authentication for critical actions, with federated identity

ADM-010 lists six critical actions that may require re-authentication: role
elevation, System Administrator assignment, sovereignty exception approval,
secret-reference change, integration credential change, production
security-policy change.

Three of those six do not exist yet (sovereignty exceptions are gate 4,
integration credentials are gate 5). Declaring policy rows for actions nothing
can perform is decoration.

**Proposed:** the policy declares only the three that exist today - role
elevation, System Administrator assignment, and security-policy change - and
gates 4 and 5 add their own, exactly as the permission registry does.

Re-authentication itself: for the credential path, a password confirmation
screen. For a federated account there is no password here, so re-authentication
means a round trip to Entra with `prompt=login`, which the existing
`MicrosoftSignInController` can carry as one extra query parameter.

### D5 - What Security Overview shows

No feature defines it. **Proposed:** a read-only roll-up in the shape of
Platform Overview - the current stance of each of the four policies, the count
of secret references approaching expiry or rotation, the ADM-011 control results,
and recent security-relevant audit events. It invents no policy and adds no
control; every number on it is read from something built by ADM-009 to ADM-012.

If you would rather it stayed unbuilt until a feature defines it, say so and the
leaf keeps its "Soon" pill.

**The control that matters on `reference_identifier`:** the request refuses any
value that `Redaction::scrub()` alters. If scrubbing changes the string, it
looked like a credential, and the field is refused with a message saying so.
That turns "never store a secret here" from a comment into a check. It is
belt-and-braces on top of a length cap and a format rule per provider.

No change to any existing table.

## 6. External APIs, identity, permissions and tenant settings

No new Microsoft API call. The only change to the Microsoft path is one extra
query parameter, `prompt=login`, on a re-authentication redirect - a documented
OpenID Connect parameter, not a new endpoint or scope.

The Microsoft Integration Freshness Rule therefore has nothing to verify for
this gate. ADM-009's Allowed Tenant ID is validated as a GUID and compared
against the `tid` claim already being read; it configures an existing check
rather than calling anything.

Four new permissions, following the `<module>.<resource>.<action>` format:

| Key | Ceiling | Auto-granted from | Risk | Audited |
|---|---|---|---|---|
| `admin.security.view` | System Administrator | System Administrator | Normal | No |
| `admin.security.update` | System Administrator | System Administrator | High | Yes |
| `admin.secrets.view` | System Administrator | System Administrator | Normal | No |
| `admin.secrets.manage` | System Administrator | System Administrator | High | Yes |

All four sit at System Administrator. Security policy is not delegated to the
Administrator tier in this gate; SEC-DEC-020's open question about Administrator
read grants stays open and is not widened here.

## 7. Data classification, retention and geography

| Data | Classification | Personal data? | Retention | Storage | Processing |
|---|---|---|---|---|---|
| `security_policies` rows | Internal, configuration | No | Configuration history, seven-year baseline pending PDPA-03 | Singapore | Singapore |
| `secret_references` rows | Internal, **metadata about credentials** | `owner_user_id` links to a person | Life of the credential plus audit baseline | Singapore | Singapore |
| Session rows, if D3 is approved | Internal, **contains `ip_address` and `user_agent`** | **Yes** | Session lifetime; rows are deleted on expiry | Singapore | Singapore |
| Audit events for policy changes | Restricted | Actor id, IP | Seven-year baseline | Singapore | Singapore |

**Sovereignty:** nothing in this gate stores or processes anything outside
Singapore. No cross-geo setting is introduced and the existing cross-geo
defaults stay OFF.

**PDPA note.** If D3 is approved, `sessions` becomes a sixth table holding
personal data, and DEC-002's PDPA-01 must add it to the access-and-correction
scope. Session rows are short-lived, which helps, but "not listed" is how a
table gets missed. This is recorded here so gate 4 inherits it rather than
rediscovering it.

**`secret_references` deserves its own line.** Metadata about credentials is
itself a target: a list of every secret this system depends on, where it lives
and when it expires, is a map for an attacker. That is why both permissions sit
at System Administrator, why the reference identifier is length-capped and
scrub-checked, and why the screen shows a provider and a pointer but never
resolves the pointer.

## 8. Security controls and threat considerations

| Threat | Control |
|---|---|
| A secret value pasted into `reference_identifier` | Refused if `Redaction::scrub()` alters it; length capped; audited |
| Policy weakened quietly | Every write audited with before/after and a reason; high-risk keys require the reason |
| Policy change by someone without authority | Tier checked in the service, not only the route - the console and a job reach the service directly |
| Cross-organisation policy or secret read | Global organisation scope on both tables, failing closed |
| Session fixation on re-authentication | Session id regenerated on every successful re-auth |
| HSTS issued in error and cached by browsers | Policy-switched, defaults OFF, screen states it cannot be withdrawn |
| CSP breaking the shell silently | Report-only mode available as a policy value before enforcing |
| Lockout used as denial of service | Lock is per address-and-network pair, as today, not per account alone |
| Idle timeout set to something absurd | Catalogue validation bounds it; the service refuses out-of-range values |
| An administrator locking themselves out of the security screens | The last-System-Administrator invariant from gate 2 still holds; no policy value can remove `admin.security.update` from the last one |

## 11. Rollback

Both migrations have working `down()`. The two middlewares are registered in
`bootstrap/app.php` and removing those two lines returns the application to its
current behaviour without a deploy of anything else. No existing table is
altered, so a rollback of this gate cannot damage gate 1 or gate 2 data.

The one irreversible item is D3: switching `SESSION_DRIVER` signs everybody out,
and switching back signs them out again. That is why it is a separate approval.
