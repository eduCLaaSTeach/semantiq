# Solution Development Kit Rules

These rules govern solution planning, controlled task execution, project tracking, and the persistent core repo generated by the Claude Solution Development Kit.

## Authority And Precedence

1. The repository's current root `CLAUDE.md` is the authoritative Claude Code loader. It loads this rule through gate SDK.
2. This rule is part of the gateway. It binds every session in every project the gateway is copied into, exactly as the other rules in `.claude/rules/` do.
3. For requirement intake, solution and phase planning, project task tracking, and per-task execution, this rule is the authority. It supersedes the overlapping parts of `.claude/rules/phased-workflow.md`, the sprint checklist `.claude/PROJECT-CONTEXT.md` used to carry, and the task-status parts of `.claude/rules/eod-reporting.md`. Where one of those disagrees with this rule on these subjects, this rule wins.
4. For every other domain, the current `.claude/` configuration is the authoritative source for organisation/project standards, and this rule follows it exactly: `.claude/rules/database-schema.md` for database work, `.claude/rules/review-gates.md` for the code and security review passes, `.claude/rules/secure-coding.md`, `.claude/rules/ui-ux-quality.md`, `.claude/rules/semantic-data-model.md`, and every other rule whose gate fires. Nothing here weakens or bypasses one of them.
5. A conflict between a solution requirement and a current standard is not resolved by this rule. Record it as a `STANDARD CONFLICT` and stop for a human decision. Any other conflict between sources is classified and surfaced the same way, never settled by silently choosing a winner.
6. Always evaluate the standards that exist in the repository at execution time. Do not rely on a copied or remembered older version of `.claude`.

## Context Discipline

Do not recursively preload the entire `.claude/` tree or the whole repository. Follow the root `CLAUDE.md` startup and task-gated loading instructions. Load only the rules, skills, context sections, and references required by the current planning or tracking task. Every file read costs AI usage, so read the least that answers the question.

- For task execution, read in this order and stop once there is enough: the root `CLAUDE.md` startup, `/doc/corerepo/14_AI_CONTEXT.md`, `/doc/corerepo/PROJECT_MANIFEST.yaml`, the current Task ID's entry, its linked requirements, the gates that apply, and only the code the task affects.
- Re-read all solution documents only for fresh intake, a full re-baseline, a material scope change, or a traceability or conflict question that needs them.
- Invoke a specialist agent only when its scope is relevant to the work. Do not run every agent on every task.
- Update `/doc/corerepo/` incrementally on meaningful state changes. Never regenerate it after routine edits.

## Requirement Source Of Truth

- Active solution requirements live under `/doc/solutiondocument/` and may be arranged in files and nested folders.
- Recursively inventory all active content under `/doc/solutiondocument/`.
- Do not assume fixed filenames, file counts, folder names, formats, modules, or technology stacks.
- Ignore any directory named `Archive` (case-insensitive) by default. Read archived content only when an active source explicitly references it or a human asks for historical comparison. Archived material is not authoritative unless explicitly re-approved.
- Preserve source file, folder, section, sheet, page, and screen references where possible.
- Never invent, remove, silently change, or silently reconcile a business requirement.

## Standards Baseline

Before phase planning:

1. Read the current root `CLAUDE.md` according to its loader rules.
2. Load only the `.claude` settings whose gates fire for the detected solution scope.
3. Record the standards used in `/doc/phasedocument/PROJECT_STANDARDS_BASELINE.md`.
4. Record, where available: repository commit, relevant rule/skill paths, applicable gates, unresolved standards conflicts, and any standard that materially shapes architecture or delivery.
5. Treat the baseline as a snapshot, not a replacement for the live standards. Re-check current standards whenever a plan is regenerated or materially refreshed.

## Planning-Only Gate

Until a human explicitly approves both:

- `/doc/phasedocument/02_Gap_Conflict_Report.md`
- `/doc/phasedocument/MASTER_PHASE_PLAN.md`

Claude must not implement application code merely as part of planning. Planning outputs may be created or updated under `/doc/phasedocument/`, together with the planning and current-state records in `/doc/corerepo/`.

## Required Planning Workflow

1. Load current repository standards through the root Claude gateway.
2. Inventory active solution documents recursively.
3. Build solution understanding.
4. Build requirement register and traceability.
5. Build the complete feature and function inventory.
6. Identify gaps, conflicts, ambiguities, and assumptions, and give every source item its disposition.
7. Derive architecture subject to both approved requirements and current standards.
8. Build dependency map.
9. Run the Phase 1 infrastructure readiness baseline through `infra-readiness-agent` for the checks that are safe and possible now, and mark every other check as not verified.
10. Generate implementation phases, no more than five.
11. Perform independent QA review, including whether every source item carries a disposition.
12. Produce the master phase plan.
13. Update the planning and current-state records in `/doc/corerepo/` through `core-repo-maintainer`.
14. Stop for human approval.

## Requirement Completeness And Dispositions

Every identified requirement, workflow step, menu, feature, function, report, analytic, integration, AI capability, data requirement, security rule, and acceptance condition receives one traceable disposition. Nothing disappears silently.

Use only:

- `Covered`
- `Duplicate`
- `Conflict`
- `Gap`
- `Out of Scope - Explicit`
- `Deferred - Approved`
- `Not Applicable - Verified`

The classification labels above classify a finding. A disposition records where each source item ended up. They work together: an item carrying the `Conflict` or `Gap` disposition traces to the `CONFLICT`, `STANDARD CONFLICT`, or `GAP` finding behind it.

- Record each disposition in `/doc/corerepo/04_REQUIREMENT_COVERAGE.md`, mapped to its source in `/doc/solutiondocument/`, and give every feature and function an entry in `/doc/corerepo/03_FEATURE_FUNCTION_INDEX.md`. Both files map to the requirements and never replace them.
- `Out of Scope - Explicit` needs a source or a human decision that says so. `Deferred - Approved` needs a recorded human approval. `Not Applicable - Verified` carries its reason and evidence.
- An unresolved material `Conflict` or `Gap` blocks the planning and build work it affects until a human resolves it.
- Never drop an item to make it fit the phase model, a task boundary, or a newer version of this kit.

## Five Macro Phases

A solution is planned in no more than five macro phases, with phase IDs `P01` to `P05`. Detailed implementation belongs in tasks and subtasks, never in extra phases, so a module, a technology, or a layer never gets a phase of its own. A smaller solution uses fewer phases only where a phase genuinely does not apply, and the plan says why. It never uses more than five.

The phases carry the delivery stages themselves: design happens in Phase 3, the build in Phase 4, and user acceptance in Phase 5. Each task inside a phase still runs Gates 1 to 6 under the Approved-Task Execution Gate below.

### Phase 1 - Platform, Infrastructure & Master Foundation

- Platform, runtime, repository, and hosting readiness.
- Frontend and backend startup readiness.
- Database ownership and connectivity, with the schema source of truth and the migration tool recorded per `.claude/rules/database-schema.md`.
- The Master DB baseline: the reusable tables and the reference and master data the features depend on.
- Availability of the existing integrations and services the solution needs.
- Baseline indexing considerations.

### Phase 2 - Core Application, Login, Administration & AI Foundation

- The application shell, per `.claude/rules/ui-ux-quality.md`.
- Login, session, and logout, following the application's authentication model as recorded in `.claude/PROJECT-CONTEXT.md`, planned whether or not the solution documents mention sign-in.
- Authorisation and RBAC, which means the application's own per-feature authorisation: the feature registry, roles as named sets of feature grants, and enforcement at all four layers, per the role and access model in `.claude/rules/ui-ux-quality.md`.
- Application administration and system administration, the security audit trail per `.claude/rules/secure-coding.md`, and configuration.
- Where the solution calls an AI model, the shared AI integration, which means the AI model catalog per `.claude/rules/ai-model-catalog.md`, with its governance per `.claude/rules/ai-agent-governance.md` and the guardrails per `.claude/rules/ai-guardrails.md`.

### Phase 3 - Feature / Function Design & Dependency Approval

- The complete feature and function index, and the dependency check for each feature.
- The explicit design of every technical workstream: Frontend, Backend, Database, Integration/API, AI, and Security.
- Gate 1 plan, design, and evaluation, and its human approval.
- The logical data proposal, the schema reuse search, and the indexing and idempotency decisions.
- The approved physical table and field proposal where one is required.

### Phase 4 - Feature / Function Build & Technical Verification

- The approved migration, authored through the confirmed migration tool.
- The schema self-check and `SCHEMA VERIFIED` before any database-dependent code.
- Explicit coding authorisation.
- The build in order: database verified -> backend -> backend tests -> frontend -> integration and AI -> end-to-end validation.
- The code and security review passes per `.claude/rules/review-gates.md`, and internal verification.

### Phase 5 - UAT, Acceptance & Release Readiness

- User acceptance testing, rework, and regression.
- Permission and security validation.
- Data, index, and performance validation where applicable.
- Idempotency and retry validation where applicable.
- AI guardrail validation where applicable, per `.claude/rules/ai-guardrails.md`.
- Explicit user approval, the completion and time log, and release readiness. Release readiness does not approve a production deploy or a migration, which still needs its own explicit approval per `.claude/rules/deployment.md`.

A phase is not accepted until all its mandatory acceptance criteria pass.

## Post-Approval Task Planning

After explicit approval of the two planning gate documents, Claude may generate project tracking artefacts through `/generate-project-tasks`.

Convert the approved Phase Plan into:
`Phase -> Module/Menu or Workstream -> Task -> Subtask`

Each task must include:

- stable task ID;
- source phase;
- module/menu/workstream;
- requirement IDs and source feature/function IDs;
- dependencies;
- applicable standards/gates;
- each explicit technical workstream, below;
- acceptance criteria;
- user testing requirement;
- status.

Before publishing tasks, prove that every active source requirement, feature, and function carries a disposition and, where applicable, maps to a task.

Task IDs follow one standard:

- Phase: `P01` to `P05` only.
- Module/Menu: `M01`, `M02`, ... within the project.
- Task: `P03-M01-T001`.
- Subtask: `P03-M01-T001-S01`.

Never renumber or delete a Task ID once it is published. Add a new ID at the end of its sequence, and preserve every prior task, event, and acceptance record. A task that is no longer wanted goes to `Cancelled` and keeps its ID. A Task ID published before the five-phase model keeps its ID and is mapped to the macro phase it now belongs to.

## Explicit Technical Workstreams

Every feature and every task states each of these explicitly:

- Frontend
- Backend
- Database
- Integration/API
- AI
- Security
- Tests/Verification
- Acceptance/UAT
- Indexing requirement
- Idempotency requirement

A workstream that does not apply is recorded as `Not Applicable - Verified` with its reason and evidence, never omitted. The workstreams describe one feature from every side. They are not separate frontend and backend phases, and delivery stays feature-oriented and end to end.

## Indexing

Evaluate indexing for every persisted structure a task creates or changes, from its approved access patterns: keys, joins, filters, sorts, tenant, status, and date lookups, uniqueness, analytics, and performance. Do not index every column by default.

- Record the decision in the task's Indexing requirement as `Required`, `Existing`, or `Not Applicable - Verified`, with the access pattern behind it.
- The physical proposal names the indexes and constraints the access patterns need (Gate 3), and the schema self-check verifies them wherever the schema source exposes them (Gate 4). An index goes through the same verification, preview, and migration workflow as a table or a column, per `.claude/rules/database-schema.md`.
- Take the access patterns from the declared grain, the keys, and the confirmed analytics questions, per `.claude/rules/semantic-data-model.md`.

## Idempotency

Design and test idempotency wherever a retry or a duplicate delivery can cause a duplicate or harmful side effect: webhooks, queues, imports, external callbacks, background jobs, AI-triggered actions, and transactional creates, where they apply. Do not force it onto simple reads or onto operations where it adds nothing.

- Record the mechanism in the task's Idempotency requirement, such as an idempotency key, a business unique key, or a dedupe record, and test the duplicate and retry behaviour. Record an operation that needs none as `Not Applicable - Verified` with the reason.
- `.claude/rules/resilience.md` is the primary home for retry safety and idempotency keys, and governs how the mechanism is built.
- A business unique key or a dedupe record is a persisted structure. It goes through the data gates like any other, per `.claude/rules/database-schema.md`, and the decision whether a repeat is a new row or an occurrence on the existing one follows `.claude/rules/semantic-data-model.md`.

## Task Status Model

Use only:
`Planned -> Ready -> In Progress -> Implementation Complete -> User Testing -> Accepted`

Exceptional states:
`Blocked`, `Rework Required`, `Cancelled`

A task counts as final project completion only at `Accepted`. A task the user rejects in testing goes to `Rework Required`, never to a separate rejected state, and a task that is dropped goes to `Cancelled`.

## User Acceptance

Never mark a task Accepted from coding completion, automated test success, developer confirmation, or silence. `Accepted` requires explicit user approval after applicable user testing.

## Time Tracking

Record actual lifecycle timestamps. Never guess time. Distinguish:

- active implementation time;
- implementation elapsed time;
- user testing elapsed time;
- end-to-end cycle time through approval.

Do not present end-to-end cycle time as developer effort.

## Approved-Task Execution Gate

After project tasks have been generated, application implementation is controlled per Task ID. Never treat backlog generation as permission to code.

A developer starts implementation only by naming one approved task, normally through `/execute-approved-task <TASK-ID>`. Claude must execute the following gates in order and stop at every approval boundary.

### Gate 1 - Plan, Design And Evaluate

Before changing code, Claude must:

- read the compact project context in the order Context Discipline sets, then the selected task, linked phase, feature, requirements, dependencies, acceptance criteria, and current applicable repository standards;
- confirm the task is `Ready`, all mandatory dependencies are satisfied, and no unresolved material `Conflict` or `Gap` blocks it;
- evaluate existing implementation and reusable components before proposing new work;
- produce the implementation plan, design approach, affected screens/services/integrations, risks, validation approach, and applicable rule gates;
- design each technical workstream under its own heading: Frontend, Backend, Database, Integration/API, AI, Security, Tests/Verification, Acceptance/UAT, Indexing, and Idempotency, using `Not Applicable - Verified` with the reason for one that does not apply;
- identify whether persistence/schema work is required.

Stop for explicit human approval of the task plan/design. Do not proceed merely because the task exists in the approved backlog.

### Gate 2 - Logical Data And Field Proposal

If the task requires persistence or changes data structures, Claude must first propose the logical data needed to satisfy the approved requirements and analytics questions. Include data entities/concepts, field/business meaning, type intent, required/optional status, validation, relationships, business time, audit/history needs, analytics use, and source requirement IDs.

This is a logical proposal only. Do not invent or claim physical platform table/column names. Stop for explicit human approval.

If the task needs no persistence/schema change, record `NO DATA MODEL CHANGE REQUIRED` with evidence and continue only after plan/design approval.

### Gate 3 - Physical Table Proposal Against The Schema Source

Gate D from the repository standard applies. Claude must read the project's schema source recorded in `.claude/PROJECT-CONTEXT.md`, check reusable existing structures first, and verify every referenced physical table/column against that source in the current session, per `.claude/rules/database-schema.md`.

Claude may prepare a physical table/field proposal only after the logical proposal is approved. The proposal must distinguish:

- existing verified tables/columns to reuse;
- approved new or changed structures that still need a migration;
- mapping from logical fields to physical fields;
- keys, relationships, and the indexes and constraints the access patterns require, per Indexing above, where supported by the governing standard;
- analytics/semantic hand-off.

Show the exact shape and do not execute DDL. Stop for explicit human approval of the physical proposal.

### Gate 4 - Migration And Schema Self-Check

After the physical proposal is approved, the migration that expresses it is authored through the confirmed migration tool, per `.claude/rules/database-schema.md`. Authoring it does not apply it: running a migration against any environment is a deployment action that still needs explicit approval, per `.claude/rules/deployment.md`.

Once the change exists in the schema source, Claude must self-check it against the approved physical proposal: table names, column names, data types, nullability/required intent, keys, relationships/constraints, the index evidence the source exposes, and any required reuse decision. Where the recorded source is the database's own metadata, the structure must be visible there. Never infer it from chat confirmation, screenshots, or a remembered schema.

If any material mismatch exists, stop and report `SCHEMA VERIFICATION FAILED`. Do not code around the mismatch.

If the schema source cannot be read, stop. Never fall back to guessed schema or direct SQL.

When the self-check passes, record `SCHEMA VERIFIED` with the verified objects.

### Gate 5 - Coding Authorisation And Implementation

Passing schema verification is not itself permission to code. Claude must wait for explicit human authorisation to proceed with coding for the named Task ID.

Once authorised:

- log `TASK_STARTED` using a real timestamp;
- implement only the selected task and approved subtasks, normally in dependency order: database verified -> backend -> backend tests -> frontend -> integration and AI -> end-to-end validation;
- use only verified physical schema names for database-dependent code;
- follow all current CODE/REV/U/AUTH/A/R/AI/AIM/DEP/etc. gates that fire;
- run required tests and validation, including the duplicate and retry tests the task's Idempotency requirement calls for;
- run independent code-reviewer and security-reviewer passes where the repository standard requires them;
- do not start another Task ID automatically.

When implementation and internal validation finish, log `IMPLEMENTATION_COMPLETED`, update the task to `Implementation Complete`, update the affected `/doc/corerepo/` sections incrementally through `core-repo-maintainer`, and stop for user testing.

### Gate 6 - UAT And Acceptance

Move the task to `User Testing` only when it is ready for the user.

- User approval -> log `USER_TESTING_APPROVED`, mark `Accepted`, update completion/time reporting, and update the affected `/doc/corerepo/` sections through `core-repo-maintainer`.
- User rejection -> log `USER_TESTING_REJECTED`, mark `Rework Required`, capture the exact feedback, and return only the affected task through the relevant gates.

Never mark `Accepted` based on Claude self-test, developer statement that coding is finished, automated tests, or silence.

## Database Gate Exception

The logical-data, physical-table, and schema self-check gates apply only when a task creates, changes, maps to, or depends on persisted structures. A task with no persistence impact still requires Gate 1 plan/design approval before code and Gate 6 user acceptance after implementation.

## Infrastructure Readiness

`infra-readiness-agent` proves the project foundation is usable before work that depends on it proceeds. It runs in Phase 1 and again whenever the hosting, runtime, repository, environment, database, an external service, the deployment target, or AI connectivity materially changes. It builds no business feature.

- It checks only what the active solution requires, and loads only the gates that apply.
- It maintains `/doc/corerepo/02_INFRA_READINESS.md`: each check's status with its evidence, when it was last verified, the blockers, and the next action.
- Never claim READY without evidence. A check that was not actually run is not verified, and documentation alone is not evidence where the repository standard requires a live check.
- Record each store's schema source of truth and migration tool per `.claude/rules/database-schema.md`, never inferred from the engine. Where the schema source cannot be read, database-dependent work is BLOCKED.
- Never put a secret or a full connection string in the record, per `.claude/rules/secret-handling.md`.

## Persistent Core Repo

`/doc/corerepo/` is the project's compact, vendor-neutral living memory, written so a developer, Claude, or any other AI-assisted development tool can pick the project up without rediscovering the whole repository. `core-repo-maintainer` maintains it. It holds:

- `00_PROJECT_INDEX.md`
- `01_CURRENT_STATE.md`
- `02_INFRA_READINESS.md`
- `03_FEATURE_FUNCTION_INDEX.md`
- `04_REQUIREMENT_COVERAGE.md`
- `05_CODE_KNOWLEDGEBASE.md`
- `06_DB_MODEL.md`
- `07_ENTITY_MODEL.md`
- `08_INTEGRATION_REGISTER.md`
- `09_AI_COMPONENT_REGISTER.md`
- `10_TASK_STATUS.md`
- `11_DECISION_CONFLICT_REGISTER.md`
- `12_CHANGE_LOG.md`
- `13_HANDOVER.md`
- `14_AI_CONTEXT.md`
- `PROJECT_MANIFEST.yaml`

Each fact is recorded once, in the store that owns it, and referenced from the others:

- It is its own store, not a knowledge-base tier, and the approval gate in `.claude/rules/knowledge-base.md` does not govern it. It is written as the work happens: the two working-memory files below as work proceeds, and every other file on accepted or verified state changes only.
- It owns no requirement. `03_FEATURE_FUNCTION_INDEX.md` and `04_REQUIREMENT_COVERAGE.md` map to `/doc/solutiondocument/`, which stays authoritative.
- It owns no task status. `10_TASK_STATUS.md` and the manifest's task fields are a snapshot of `/doc/tasktracking/`, which stays the record.
- `06_DB_MODEL.md` records only physical structures verified against the project's schema source (`SCHEMA VERIFIED`), never from memory. The table dictionary rules in `.claude/rules/knowledge-base.md` still apply.
- In a project that uses this kit, it is where the working-memory log lives: `01_CURRENT_STATE.md` holds the current focus and progress, and `11_DECISION_CONFLICT_REGISTER.md` holds the dated decision log and the open questions. Those two files are updated as work proceeds, like the working-memory log in `.claude/rules/knowledge-base.md`: a change of focus or progress, a dated decision, a new open question.
- `13_HANDOVER.md` is the project-level handover. The session handoff written by `/session-handoff` stays for a single session.
- The orientation map reads it as one more source and owns no fact of its own, per `.claude/rules/orientation-map.md`.

Keep it current and small:

- Outside the two working-memory files, update only the files and sections an accepted or verified change affects. The changes that count: infrastructure readiness moving; a feature or function added, removed, deferred, accepted, or re-scoped; a conflict resolved; a structure verified or changed; an entity relationship, an integration, or an AI component changed; a task changing major lifecycle state; an accepted change to important structure or entry points; and a handover requested or a task or phase closing.
- Never regenerate it after a routine edit, an intermediate code change that is not accepted or verified, or a read that changed nothing.
- `05_CODE_KNOWLEDGEBASE.md` is a map of paths and symbols, never a code dump.
- `14_AI_CONTEXT.md` and `PROJECT_MANIFEST.yaml` stay short: the current state and the next action, not the history.
- Write it in vendor-neutral language. `.claude/` stays Claude-specific.
- Never put a secret, token, credential, full connection string, customer record, or production value in it, per `.claude/rules/secret-handling.md`.

## Kit Upgrade Safety And History Preservation

Upgrading the gateway, or this kit inside it, in an existing project is governance and tooling maintenance, never permission to redesign or recode the application.

Before changing kit files in an existing repository:

1. Reach a safe checkpoint. Do not upgrade mid-task, mid-schema change, mid-deployment, or partway through a UAT defect fix unless the owner explicitly accepts that risk.
2. Inventory the current root `CLAUDE.md`, `.claude/`, `/doc/solutiondocument/`, the phase outputs, the published Task IDs, the task-event history, the UAT and acceptance records, the approved data proposals and schema verification evidence, `/doc/corerepo/`, and the current Task ID with its gate and status.
3. Create or confirm a Git rollback checkpoint, and make the change on a dedicated branch where possible, per `.claude/rules/git-branching-release.md`.

Preserve the project's history and standards:

- Never overwrite the project's root `CLAUDE.md`, `.claude/PROJECT-CONTEXT.md`, or any organisation/project standard wholesale because the kit carries a file of the same name. Merge the newer version into them, so nothing the project holds is lost or weakened.
- Never delete or renumber a published Task ID. Keep a legacy ID and map it to the macro phase it now belongs to.
- Never rewrite a historical lifecycle timestamp, a UAT approval, an acceptance record, or the task-event history.
- Never remove an active requirement, feature, or function to fit the newer kit. Compare coverage instead, so each one keeps its disposition.
- Never run DDL, a migration, a deployment, or application feature coding as part of the upgrade.
- Never reset `/doc/corerepo/` or the task tracking history. Update only the kit-owned governance templates and the affected current-state summaries.
- Where the upgrade materially changes architecture, security, data, UI, AI, API, deployment, or acceptance for an approved plan, propose a refresh or a mapping only. The approved plan and its tasks stay in force until a human explicitly approves the refresh.

After the upgrade, and before the upgrade branch is merged, run a post-upgrade validation that proves:

- requirement and feature counts and their dispositions are still complete;
- Task IDs and the event history are preserved;
- accepted decisions and schema verification evidence are intact;
- the current standards still take equal or stronger precedence;
- no unintended application code, schema, or deployment change occurred;
- the current task resumes from the same gate and status;
- every kit command still resolves to its expected controlled sequence.

Record the result as `PASS - SAFE TO MERGE` or `FAIL - DO NOT MERGE`. On a fail, stop, do not merge the upgrade branch, restore or reconcile from the pre-upgrade checkpoint, and validate again.

## Final Reporting

For solution planning and task work, report: the planning documents written or updated under `/doc/phasedocument/`, and whether `02_Gap_Conflict_Report.md` and `MASTER_PHASE_PLAN.md` are explicitly approved or still awaiting approval; the active sources reviewed and any `Archive` content excluded; the standards baseline recorded in `PROJECT_STANDARDS_BASELINE.md`, with the commit, the gates loaded, and any material standards drift found since it was taken; the number of macro phases planned, never more than five, and the reason for any of the five not used; the count of source items per disposition, and every unresolved material `Conflict` or `Gap` with the work it blocks; the open `GAP`, `CONFLICT`, `ASSUMPTION REQUIRED`, and `STANDARD CONFLICT` items; the infrastructure readiness status recorded in `/doc/corerepo/02_INFRA_READINESS.md`, naming every check not verified; the tracking artefacts written under `/doc/tasktracking/`; each Task ID touched and every status transition it made within the task status model; the explicit technical workstreams recorded for each task touched, with the reason for each `Not Applicable - Verified`; the indexing and idempotency decisions, and the duplicate and retry tests run; the events appended through `scripts/task-event.sh`, with their real timestamps or the reason a timestamp could not be captured; each gate passed for the Task ID and who approved it, including the explicit coding authorisation; the data and schema gate state, which is `NO DATA MODEL CHANGE REQUIRED`, the logical and physical proposals and their approval, the migration authored, `SCHEMA VERIFIED` with the verified objects, or `SCHEMA VERIFICATION FAILED` or an unreadable schema source and where work stopped; the user testing outcome, which is `Accepted` on explicit user approval or `Rework Required` with the exact feedback captured; the `/doc/corerepo/` files updated, or that the change needed none; when a kit upgrade ran, the post-upgrade validation result, `PASS - SAFE TO MERGE` or `FAIL - DO NOT MERGE`, and what failed;
