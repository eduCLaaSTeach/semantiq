# Secure Coding Rules

Claude must write code that treats every input as hostile until the server has checked it, encodes every output for the place it lands, keeps the browser's protections switched on, and leaves an audit record of every security-relevant action. The review passes find these defects after they are written. This rule is what keeps them from being written.

Applies to every task that writes or edits code that will be delivered, so it fires with gate CODE. It does not override `.claude/rules/secret-handling.md`, `.claude/rules/database-schema.md`, `.claude/rules/production-readiness.md`, or the DDL restrictions.

`.claude/rules/production-readiness.md` already requires validating external input at boundaries and using safe framework and database APIs instead of string concatenation. This rule is the detail behind that line. The error contract for a service interface stays in `.claude/rules/api-design.md`, dependency vetting stays in `.claude/rules/enterprise-governance.md`, and the role and access model stays in `.claude/rules/ui-ux-quality.md`. Cross-reference rather than duplicate.

## Assume No Security Stack

- Do not assume the templating engine and its escaping, the HTML sanitizer, the CSRF mechanism, the session cookie attributes, the content security policy and security headers, the origins allowed to read responses cross-origin, whether the server fetches supplied URLs and which internal destinations it may reach, whether uploads are accepted with their types, size, storage, and scanner, the audit trail location and audited action set, or the dependency audit tool. Each is recorded in the Secure Coding Conventions section of `.claude/PROJECT-CONTEXT.md`.
- Ask for one only when the change depends on it, and record the answer. Leave any other unasked and out of the report. Three default safely without a question: with no sanitizer confirmed, rich content renders as text; with no origins confirmed, cross-origin reads are refused; with no content security policy confirmed, none is added or loosened.
- Prefer the framework's own protection over a hand-built one. A framework's escaping, CSRF middleware, and parameter binding have been tested against these attacks in every project that uses them; a custom replacement has not.
- Do not introduce a security library, sanitizer, or scanner the project has not approved, per `.claude/rules/enterprise-governance.md`. Propose it instead.

## The Server Decides What Is Valid

- Validate every value that crosses a trust boundary on the server: form fields, query strings, route parameters, headers, cookies, uploaded files, webhook bodies, queue messages, and responses from another service. A value the application stored earlier is still input when a user could have influenced it.
- Browser-side validation is a usability feature, never the control. Anyone can send the request without the page, so every rule a form enforces is enforced again on the server.
- Check type, format, length, range, and whether the value is required, and reject what does not conform rather than repairing it silently. Prefer an allow-list of what is permitted over a deny-list of what is not.
- Bind a request to an explicit set of fields. Never mass-assign a request body onto a record, because that is how a caller sets their own role, owner, tenant, or approval flag by adding one field to the request.
- Validate the canonical form: decode, normalize, and resolve a value before checking it, not after.
- Completing a step-by-step draft re-validates the whole stored payload against the record's full rules and binds it through the record's explicit field list, because a step save can arrive out of order or carry another step's fields.

## Input Never Becomes Syntax

- Pass values to a database as bound parameters through the confirmed data-access layer, never concatenated into query text. That holds for raw queries, stored procedure calls, and an ORM's raw-expression escape hatch alike.
- A parameter cannot hold an identifier. A sort column, a sort direction, a table name, or a field list taken from a request is checked against an allow-list of known names and mapped to the real one, never passed through. Every list screen sorts from the URL query, per `.claude/rules/ui-ux-quality.md`, so this is the common case rather than an edge.
- Run an operating-system command with its arguments as a separate list, never through a shell with input interpolated into the command string. A value in that list can still be read as an option: place it after the `--` end-of-options marker where the program supports one, and reject a value that begins with `-` where it does not. Prefer a library call over a command where one exists.
- Resolve a file path from an identifier the application issued, never from a name the user supplied. Where a supplied name is unavoidable, canonicalize both the path and the base directory with symlinks resolved, and confirm the path sits inside the base, compared with a trailing separator rather than as a bare string prefix.
- The same holds for every other interpreter a value can reach: a template, a regular expression, an LDAP or XPath query, a response header, a log line. Reject or encode line breaks and control characters wherever a value is written into a line-oriented format.

## Encode Output For Where It Lands

- Escape every value written into a page for the context it lands in. A template engine's automatic escaping covers HTML body text and quoted attribute values; leave it on. Percent-encode a value placed into a URL component. Never place a value a user could influence in an event-handler attribute, a `style` attribute or `<style>` block, or an unquoted attribute, where HTML escaping does not protect it.
- Never build markup by concatenating a value a user could influence, and never switch escaping off for one. Where rich content is a genuine requirement, run it through the confirmed HTML sanitizer with an allow-list of tags and attributes, and render only what the sanitizer returns. User-supplied Markdown is rich content: render it with raw HTML disabled, then sanitize the output. Where no sanitizer is confirmed, render the content as text.
- Pass data to a script as JSON, never by writing a value into inline JavaScript. In a data attribute, write the JSON through the template's normal attribute escaping, which encodes quotes as well. In a JSON script block, escape `<`, `>`, and `&` the way the framework's JSON-for-HTML helper does it, never as raw encoder output.
- Check the scheme of any user-supplied URL before rendering it as a link or a source. Allow `https` and the schemes the feature genuinely needs, never `javascript:` or `data:`.
- In client code, write a value a user could influence into the page through text APIs, not HTML APIs. Setting `innerHTML`, or a framework's equivalent, from such a value is the client-side form of the same defect.
- Encode for every other place a value lands, not only a page. In a CSV or spreadsheet export, write numbers as numbers and prefix a text cell that begins with `=`, `+`, `-`, `@`, a tab, or a carriage return with a single quote, so it opens as text rather than running as a formula, and write every cell through the CSV writer's quoting, so a separator or line break inside a value cannot start a new cell. Escape a value written into an HTML email body exactly as on a page.
- Send a record out through an explicit field list for its audience, never the whole model. A credential hash, a token, a key, a secret field, or an internal flag never leaves in a response, a page, or an export because it happened to be on the object.
- Before a change first sends personal or sensitive data somewhere new (a third-party service, a webhook, an email, an export, or a model), classify those fields per `.claude/rules/data-governance.md` and send only what the purpose needs, even when nothing is stored.
- Send the confirmed content security policy where the project has one, and do not loosen it to make a feature work without a documented exception.
- Model output is untrusted output too: render it as text, never as markup, per `.claude/rules/ai-model-catalog.md` and the untrusted-output baseline in `.claude/rules/enterprise-governance.md`.

## Browser Protections Stay On

- Protect every state-changing request the browser authenticates by itself, with a session or authentication cookie, using the confirmed CSRF mechanism, which is the framework's own where it has one. A route authenticated only by a credential the caller attaches explicitly, such as a bearer token, is not exposed to CSRF and needs no exemption, provided it never also accepts the session cookie.
- A safe method (`GET`, `HEAD`, `OPTIONS`) never creates, changes, or deletes application data or access, because a link or an image tag can send a `GET` and CSRF protection does not check it. The audit record of the request itself is not such a change.
- There is one standing CSRF exemption, an inbound third-party webhook route, which carries no session: register it outside the session and CSRF middleware, or exclude it there, verify the sender's signature over the raw body in constant time, and reject a replay with the signed timestamp and a replay window where the sender signs one, or a stored delivery id where it does not. Any other exemption for a cookie-authenticated route is a documented exception naming the route and the control that replaces the token.
- Set session and authentication cookies `HttpOnly`, and `Secure` wherever the application is served over HTTPS, which is always in production. Scope the session cookie to the application's own host with no `Domain` attribute, using the `__Host-` prefix wherever the application is served over HTTPS. The prefix requires `Secure` and `Path=/`, so a browser discards it over plain HTTP; set the cookie name and `Secure` from the same per-environment setting. Use `SameSite=Lax` unless the project records a reason for `Strict` and has confirmed its sign-in flow under it: where an identity provider sits on a different site from the application, the browser withholds a `Strict` cookie on the callback, so a `state` stored before the redirect cannot be read and the sign-in either skips verification or loops. `SameSite` is defense in depth beside the CSRF token, never a replacement for it.
- Send the security headers the project confirms: framing protection so the application cannot be embedded to capture clicks, content-type sniffing off, and a referrer policy that does not leak paths carrying identifiers. Add `Strict-Transport-Security` in production, and `Cache-Control: no-store` on authenticated responses that carry personal or sensitive data.
- Grant cross-origin read access only to the confirmed origins, compared by exact match, never by prefix, suffix, or pattern, and never to the `null` origin. Never echo an `Origin` that has not passed that exact-match check on a response that permits credentials, and send `Vary: Origin` whenever a checked origin is echoed back. CORS decides who may read a response, not who may send a request, so it never replaces CSRF protection.

## No Unsafe Deserialization Or Dynamic Execution

- Never deserialize untrusted data into native objects: PHP `unserialize`, Python `pickle`, Java native serialization, .NET `BinaryFormatter`, a YAML loader that constructs arbitrary types, or anything equivalent. Accept a data format such as JSON and validate it against the expected shape. JSON is safe only when the deserializer builds plain data: never enable type-name or polymorphic type handling that lets the payload name a class.
- Never evaluate, include, require, or compile code whose content or path a user can influence. No `eval`, no dynamic include, no template compiled from user input, no expression language fed request data.
- Never choose a class, a method, a callable, or a file to load from input without mapping it through an allow-list first.

## Known Insecure Patterns

- Do not introduce a known insecure coding pattern, whether or not this rule names it. The sections here are the common cases, not the whole list; the current OWASP Top 10 and CWE Top 25 are the reference for the rest.
- Parse XML with DTD and external entity processing off, including XML inside uploaded files such as SVG and office documents.
- Generate a token, a one-time code, a share link, or any other value that grants access from a cryptographically secure random source.
- Compare a secret, a signature, or a token in constant time.
- Bound a regular expression run on input, by input length or by engine, so a crafted value cannot stall a worker.

## Outbound Calls And Supplied URLs

- Never disable TLS certificate or host-name verification on an outbound call, in any environment, including to get past an untrusted or self-signed chain. Fix the runtime's trust store, or trust the confirmed internal certificate authority through configuration.
- Where the server fetches a URL a user or an administrator supplied, such as a webhook target, an import source, an AI model catalog endpoint, or a connection test, allow only the schemes the feature needs. Parse the URL once, with the same parser the client uses. Resolve the host and check every returned address, IPv4 and IPv6, refusing every address that is not globally routable unicast unless it is an internal destination the environment configuration names, per the next bullet. Check an IPv4 address embedded in an IPv6 one (IPv4-mapped, IPv4-compatible, or NAT64 `64:ff9b::/96`) as that IPv4 address, and refuse 6to4 and Teredo addresses outright; loopback, unspecified, link-local, private, unique-local, carrier-grade NAT, and cloud metadata addresses are the common cases. Connect to the checked address while keeping the original host name for TLS server name and certificate validation. Turn off automatic redirects and repeat the check on each hop, with a hop limit, and ignore proxy environment variables unless the confirmed egress proxy enforces the same policy.
- An internal destination is reachable only when the application's environment configuration names it, enumerated in the configuration contract per `.claude/rules/production-readiness.md` and recorded by name in `.claude/PROJECT-CONTEXT.md`. A catalog record, a form, or any other data never widens that list.
- Never show a user the raw response of a supplied-URL fetch or its low-level connection error, except on a screen gated to the system admin tier whose purpose is to show that response, such as the AI model catalog test call in `.claude/rules/ai-model-catalog.md`. Content the feature exists to deliver, such as the generated text calling code extracts from a model response, goes out through its explicit field list and renders as text.
- Redirect a browser only to a known route, or to a supplied target that passes one of two checks: a relative path that, after decoding and with control characters refused, starts with a single `/` not followed by `/` or `\`; or an absolute URL, containing no backslash, control character, or userinfo, whose scheme, host, and port, parsed the way the browser parses them, exactly match one of the application's registered URLs. Redirect to the URL rebuilt from those parsed parts rather than to the supplied string. Anything else goes to a fixed default. Keep a post-sign-in destination server-side rather than on the query string. An open redirect turns the application's own domain into a phishing link.

## File Uploads

Applies only where the application accepts files. Whether it does, and the confirmed types, size limit, storage location, and scanner, are recorded in `.claude/PROJECT-CONTEXT.md`.

- Enforce the size limit on the server before reading the whole file, and in the web server or proxy as well where the project confirms one.
- Allow-list the permitted types, and check the file's actual content against the type it claims. An extension and a declared content type are both chosen by the uploader, and a signature check does not catch a polyglot file, so where an uploaded image is displayed and the project confirms an image library, re-encode it rather than serving the uploaded bytes.
- Store the file outside the web root, or in storage that never executes it, under a name the application generated. Keep the original name as data, never as the path.
- Serve every uploaded file with its explicit content type and `X-Content-Type-Options: nosniff`. Serve a file whose verified type can carry active content (HTML, SVG, XML, and similar) with `Content-Disposition: attachment`, or from a separate site, a different registrable domain rather than a subdomain, that receives none of the application's cookies. A verified raster image may display inline.
- Authorize every download through the same record policy and query scope as the record the file belongs to, per the role and access model in `.claude/rules/ui-ux-quality.md`. A guessable file URL is a query with no scope.
- Unpack an archive only with limits on entry count, expanded size counted while streaming rather than after, compression ratio, and nesting depth. Refuse absolute paths, `..` segments, and symlink or hardlink entries, so no entry can write outside its directory. Check an image's declared dimensions against a pixel limit before decoding it.
- Scan for malware where the project confirms a scanner. Where none is confirmed, say so in the report rather than implying the file was checked.

## Errors Show Users Nothing Internal

- Run production with debug output off, and refuse to start in production with it on, per the configuration contract in `.claude/rules/production-readiness.md`.
- For an unexpected or unhandled error, show a user a generic message and a correlation id. Keep the stack trace, the query, the file path, the configuration, and library versions in the log, never in a page, a toast, an alert, or a response body. Expected outcomes keep their specific, safe messages: field and form-level validation per `.claude/rules/ui-ux-quality.md`, and a connection or model test result shown on a screen gated to the system admin tier, masked as `.claude/rules/ai-model-catalog.md` requires. A service interface follows its own error contract in `.claude/rules/api-design.md`.
- Keep an error from confirming what the user may not see. A record outside the user's query scope answers exactly as a record that does not exist, with the same status and body shape, on the detail, the export, and the file download alike. A feature the user holds no grant for answers as forbidden, and so does a record the user can see whose per-record policy refuses the action, per `.claude/rules/api-design.md`: the application's own features are not secret, while whether a record exists is data the user may not be entitled to.
- Log the diagnostic detail without secrets, tokens, or personal data. Identify the actor and the record by the application's own ids and the correlation id, never by a name, an email address, or another personal field, per `.claude/rules/secret-handling.md` and `.claude/rules/production-readiness.md`.

## Security-Relevant Actions Leave An Audit Record

Sign-in outcomes, grant changes, and catalog changes in `.claude/rules/ai-model-catalog.md` are part of the security audit trail. Each may keep its own table and grain, but each is durable, append-only, and free of secrets, and no action is recorded twice. This section is the general rule behind them, and it covers the actions no other rule names.

It applies when a change adds or alters one of the actions below. Where the project has no security audit trail yet, raise it with the developer per `.claude/rules/enterprise-governance.md` rather than building the store inside an unrelated change. Until the trail exists, the audited action does not ship, unless the developer accepts shipping it without an audit record and that acceptance is recorded under Documented exceptions in the Secure Coding Conventions section of `.claude/PROJECT-CONTEXT.md`, naming the action and the follow-up.

- Record at least these, whether they succeeded or were refused: a sign-in outcome; an administrator creating, deactivating, or reactivating a user account; a role, grant, or assignment change; issuing, rotating, or revoking an API key, token, or share link that grants access; a user acting as, or viewing the application as, another user; a permanent delete or purge, or an administrator restoring another user's record; an export or bulk download; a change to system, integration, or security configuration; and read access to a record the project names as sensitive, by its confirmed classification or in the audited actions recorded in `.claude/PROJECT-CONTEXT.md`.
- Each record carries the actor, as the application's own user id or the service identity, left empty only where the attempt failed before any identity was known; the action, as the feature registry code paired with a member of the shared action vocabulary in `.claude/PROJECT-CONTEXT.md`; the resource type and key; the outcome, including refused; when it happened, timezone-aware; the correlation id; the session reference where one exists; and the source address where the project confirms recording it. A change to access or configuration also carries what it was, what it became, and the authority the actor held at the time. An action the vocabulary lacks is added to it rather than kept in a separate list, per `.claude/rules/semantic-data-model.md`.
- Record a refused attempt as well, because a blocked privilege change is the only signal that somebody tried. Write it outside any transaction that rolls back, after the rollback or on its own connection, so the record survives the error that produced it.
- Write the record of a committed action in the same transaction as the action where they share a store, so the two commit or roll back together. Where the audit store cannot share that transaction, write an outbox row in the action's transaction and relay it to the audit store; never write the record only before or only after the commit. For an action with no transaction to share, such as an export, a download, or a sensitive read, write the record first and refuse the action when it cannot be written. A log line and an alert never stand in for the record.
- Never put a password, token, key, secret, one-time sign-in code, or decoded claim in an audit record, and carry no personal data beyond what identifies the actor, the resource, and the source address. Treat the source address as personal data and classify it per `.claude/rules/data-governance.md`. A change to a secret field records that it changed, never either value.
- Keep the trail append-only: no code path or screen updates or deletes an audit record. Enforce it in the store as well, by granting the application's runtime identity insert and select on the audit tables and no update or delete; select is needed both for reading the trail and for an insert that returns the new key. That is a database grant, not a schema change: surface it as a manual step per `.claude/rules/deployment.md`, route it to the database owner where the application does not own its database, record how it is enforced in `.claude/PROJECT-CONTEXT.md`, and report the trail as append-only by convention only until the grant is confirmed.
- Purging or anonymizing expired records is a retention job under `.claude/rules/data-governance.md`, run under a separate identity, never an application feature. Where a confirmed privacy regime requires correcting or erasing a person's data, pseudonymize the personal fields in the trail through that same identity and record the change as its own entry. Confirm with the developer whether the regime exempts audit records rather than assuming either way.
- Reading the trail is a feature like any other: register it, grant it, and enforce it at all four layers per the role and access model in `.claude/rules/ui-ux-quality.md`. Scope rows so no tier reads records of system or security configuration changes, or of actions by a higher tier, unless its confirmed grant says so, and never render the before or after value of a field classified as sensitive, or a stored session reference, which can be used to act on a live session.
- A log line is not an audit record. Logs rotate, are sampled, and are shaped for reading, not for answering who changed what and when. A structured log stream may mirror an audit record for alerting, never replace it.
- The audit store is persisted data: gates D, SEM, and DG apply, the action and outcome values are codified, and it takes the audit retention recorded in `.claude/PROJECT-CONTEXT.md` unless a different one is confirmed. Its grain is one row per recorded action attempt. The resource reference is a codified resource type plus the resource's key, deliberately without a foreign key, because an audit record outlives a purged resource. The actor reference carries no foreign key either, because it holds a user id or a service identity and stays empty where no identity was known. Declare both exceptions to the key rule in `.claude/rules/semantic-data-model.md` in the grain sentence and the table dictionary. Its location is a confirmed fact.

## Security Cases Are Tested

A review finds a defect once. A test proves the control holds and keeps holding. `.claude/rules/production-readiness.md` already requires negative authentication and authorization tests. Test each control the change adds or alters, not a protection the framework applies globally that the change left alone:

- a new validation rule or boundary rejects malformed, oversized, out-of-range, and wrong-type input rather than storing or repairing it;
- a new write path ignores or refuses a protected field (role, owner, tenant, approval) added to the request body;
- a new raw query, command, path, or allow-listed identifier treats an injection payload as data, and an unknown sort column is refused;
- a new render path shows a script payload as text, and a new export opens a formula payload as text;
- a new XML parse path refuses an external entity;
- a new response, page, or export carries only its listed fields, and the log lines the change emits carry no secret, token, or personal field;
- a new cookie-authenticated state-changing route refuses a request without a valid CSRF token, with enforcement switched on in the test since some frameworks skip it under the test runner, and a new CSRF exemption refuses a request that lacks the control replacing the token;
- a new or changed session cookie carries `HttpOnly`, `Secure`, and the confirmed `SameSite` value;
- a new or changed cross-origin policy refuses an unlisted origin and the `null` origin, and never echoes an unchecked `Origin` on a response permitting credentials;
- a new scope, export, or download path does not return a record outside the user's scope;
- a new redirect refuses a target outside the application's own paths and registered URLs, and a new supplied-URL fetch refuses a loopback, private, or metadata address, directly and through a redirect;
- a change to error handling or environment configuration shows, with production settings, no stack trace, query, path, or configuration;
- a new audited action writes its record, including when it is refused, and the record carries no secret;
- a new upload path rejects a disallowed, mislabelled, or oversized file, serves an active-content file as an attachment with `nosniff`, and refuses an archive entry that escapes its directory or exceeds the expansion limits.

Use synthetic payloads only, never production data, per `.claude/rules/data-governance.md`. A change that adds or alters none of these controls needs none of these tests, and the report says so.

## Final Reporting

For code work, report only the controls the change touched, one line each, and say so in one line when it touched none: trust boundaries added and how each is validated on the server; any query, command, path, or identifier handling, including an allow-listed identifier; any new render path, export, or response and its encoding, sanitizer, or field list; any CSRF exemption, or cookie, header, or cross-origin change; any deserialization, XML parsing, or dynamic loading and how it is constrained; the TLS verification of any new outbound call, the destination checks on any supplied-URL fetch, and how any redirect to a supplied target is checked; upload handling, where uploads changed; any change to error display or debug configuration; audited actions added, where the trail lives, and whether append-only is enforced by the store or by convention only; the security tests added and the security checks run, with their results, or why none could run; any Secure Coding Conventions fact the change depended on that is still unconfirmed; security impact, confirming no secret or token entered a log, an audit record, or an error, no personal data entered a log or an error, and an audit record carries no personal data beyond what identifies the actor, the resource, and the source address.

Final rule: if a Secure Coding Conventions fact this change depends on is unclear, do not guess. Ask and record it first.
