# Gateway Changelog

The version of the Claude gateway kit you have. After you pull, the top row is the current version; read down to see what changed since you last pulled. This file ships inside `.claude/`, so it travels with the kit. The same version is stamped at the top of `.claude/README.md`, and every version has a matching git tag and GitHub Release (full notes on the [GitHub Releases page](https://github.com/CLaaS2SaaS/claude-code-gateway-kit/releases)).

Current release at the top, first release at the bottom. Major releases (the `.0` of each series) are shown in **bold**.

| **v2026.15.0** | 18 August 2026 | Settle what a button looks like, because the kit was leaving it to each screen. A screen review found `Cancel` rendered as a filled button on a form footer while `Clear`, doing the same kind of job on the list beside it, was borderless, and the references disagreed with each other and with the layout template: `buttons.md` called Secondary a filled Cadmium Violet, the template rendered `.btn-secondary` as a neutral bordered control, and three emphasis levels (solid, outline, ghost) meant one action could be written three defensible ways. There are now two looks and no more. One solid button per action group, that group's one main action in its meaning-driven variant, and one neutral secondary look - surface fill, one control border, ink text - for every other labeled action, at whatever size the context needs. `btn-ghost`, `btn-outline`, the `btn-icon` modifier, and Cadmium Violet as a button fill are retired; violet stays a badge and chip color. Both looks share one geometry per size step, so only the fill, the border, and the label color ever differ, and a button now shares one height and one boundary token with the field beside it instead of carrying a second border value. The controls that are never the solid one are enumerated rather than left to judgement (`Cancel`, `Back`, `Close`, `Dismiss`, `Skip`, `Keep editing`, `Clear`, `Clear all`, `Clear filters`, `Reset`, `Reset filters`, `Apply`, `Filters`, `Export`, `Columns`, `Density`, `Duplicate`, `Test Configuration`, and every actions-column control), and a group that only changes what is on screen - a filter bar, a filter popover footer, a toolbar of view controls - carries no solid button at all, since nothing in it commits anything. That resolves an inconsistency inside the test-before-save pattern, where the test control was primary before a test and outline after it: `Test Configuration` proves a connection rather than saving it, so it is secondary in every state and the footer holds no solid button until `Save` earns it. The general form of that is now a rule of its own - a button's look never changes with its state, because a control that shifts emphasis between two states is the same defect as two screens disagreeing, only closer together - so loading swaps the label for a spinner at the same width and changes nothing else. A status meaning colors the icon and the label on the identical shell (`btn-text-danger`), never the fill, border, height, or radius. The second half of the change is the actions column: every control in one carries its visible word beside its icon (`View`, `Edit`, `Delete`, `Restore`, `Duplicate`, `Test`), because a bare pencil beside a bare key beside a bare trash asks the user to guess, puts two irreversible actions a few pixels apart with nothing to tell them apart, and explains itself only through a hover tooltip, which a touch device does not have and a keyboard user never sees. The word is visible text rather than only an `aria-label`, it stays at every breakpoint (a narrow screen scrolls the pinned actions column and grows the small control to the 44px touch minimum instead of dropping the label), and past about three row actions the rest move behind one labeled `More` overflow whose accessible name names the row. Icon-only survives as chrome on a closed list by kind - a dismiss or close mark on something dismissable, a clear mark on a field or a chip, and a form repeater's per-row remove - each with an accessible name, and never in an actions column. Adds two mandatory sections to `ui-ux-quality.md` (Two Button Looks, Everywhere; Action Columns Carry Their Labels) and rebuilds `buttons.md` section 4 around them. Wiring: three new hard stops, the always-on UI invariant in the loader, the palette role for Cadmium Violet corrected in the UI skill index and `design-tokens.md`, row-action icon concepts added to the registry catalog in `assets.md`, and updates to `tables.md`, `forms.md`, `modals-dialogs.md`, `search-filter.md`, `empty-and-loading-state.md`, `catalog-ui.md`, `README.md`, and both developer-handbook guides. The layout template was demonstrating the defect it now documents, so it was fixed too: every ghost button became the one secondary look, the tickets list's delete action was an unlabeled trash icon with no accessible name at all and the model catalog's duplicate and delete were icon-only, so all three gained their word, one delete's accessible name was corrected because "Move X to Recycle Bin" no longer contained the visible label, and the two connection footers stopped swapping their test button's emphasis as the test ran. Two further screen behaviors were settled in the same pass, both found by looking at a real screen. **Validation now reports once, where the error is.** Every field error stays inline under its own field, a blocked submit is announced by one error toast naming how many fields need attention while focus and scroll move to the first invalid field, and the error-summary card is gone: it repeated the same sentences the fields already carried, so the user read every error twice and tracked it in two places, and an error toast persists until dismissed anyway. A form-level error that belongs to no field, a failed save or an unreachable service, gets one persistent inline alert at the form foot instead, since that is the one thing no field can say; a server error that does belong to a field is mapped back onto it. That adds a third mandatory section to `ui-ux-quality.md` (Validation Reports Once, Where The Error Is), a hard stop, and updates to `forms.md` and `toasts.md`. **And the layout template's tickets list now demonstrates pagination** rather than explaining why it has none: the demo set carries thirty rows, so the footer reads "Showing 1-25 of 30" over a working pager with the rows-per-page select (25 / 50 / 75 / 100), previous and next as the pager's own icon-only members, the page and the size in the URL beside the sort and the filters, a return to page one on any filter, sort, or size change, and page controls that appear only past one page so nothing dead is ever rendered. A `Many` demo state pads the set to 247 rows so the collapsed range (`1 2 3 4 ... 10`) and the size select can be seen working. Four adversarial sweeps over the change raised fifty-eight findings between them - two over the button work, one over the documents as a set, and one tracing the layout template the way a browser would run it - and every genuine defect was fixed before release. From the document sweeps: the discard dialog's three-way footer still shipped two solid buttons, `Test call` and `Test Configuration` were one control under two names with only one of them on the rule's list, `Search` was on that list while the search component ships no such button, the neutral border was described as one shared value and defined as two, `--badge-danger-fg` was used by the new CSS and declared nowhere in it, the closed icon-only list omitted the toast dismiss and filter-chip clear marks the kit ships, `btn-text-success` was defined and never used, the promised shared icon size had no value anywhere, three cross-references pointed at renamed or non-existent sections, and a toast's inline action, a date-preset row, a notification pill, an entity card's action cluster, and the pager each carried a look the two-look rule had just retired or had never accounted for. "Action group" is now defined too, since several of those arguments came from its absence: one cluster of controls the user chooses between in one place, so a page-header CTA and a failed region's `Retry` do not compete. Two pre-existing shell issues the sweeps surfaced are recorded as follow-ups rather than folded in: the rail brand block is a `div` carrying `role="button"`, and the `.ic` icon class is used across the skill and defined in none of it. Two smaller placements were pinned down in the same release. **Every toast now appears at the top right, and nowhere else.** Placement was PRINCIPLED with a table of four corners and a "default" top-right, which is how the layout template ended up pinning its assertive region to the bottom right: a success surfaced top right and an error surfaced bottom left of it, so the user had two places to watch. The section is now ENFORCED with no table: one host anchored top right, offset below the top-bar height so a toast never covers the top-bar utilities it sits beside, newest nearest the top edge, with the polite and assertive live regions inside that one host so politeness decides how a message is announced and never where it appears. A narrow screen widens the same top edge rather than moving to another corner, and a toast that would cover something important is answered by offsetting the host once for the whole app, not by moving that screen's toast. Adds a hard stop, and updates `toasts.md`, the loader invariant, `README.md`, and both handbook guides. **And the template's two demo-state switchers now say they are demo controls**, the way the role switcher already did: a `Template only` badge beside the label and an info icon explaining that the control previews the data, many-rows, empty, and error states side by side, that it is not a product feature, and that a real app reaches each of those states from its own data - rows or no rows, a filter that matches nothing, a request that failed. Three follow-ups from reviewing the template on screen close the release. **A ticket can be edited.** The list carried View and Delete and no way in, so the row gained a labeled `Edit` and the record's own action cluster did too, both routed to the shared form: `ticket-new` becomes `ticket-form`, serving create and edit from one template keyed on whether the record exists, the way the form archetype already described and only the model catalog demonstrated. In edit mode the title, the breadcrumb leaf, the submit label, the loading verb, and the toast all follow the mode. **Breadcrumbs are generated from the navigation config and carry the full path.** They were hand-written per page, which is why the ticket detail read `Tickets / INC-1029` under a separate `All Tickets` back link: two rows saying the same thing, and a path missing the cluster it sits in. It stays deliberately plain: an ancestor that is a real page is a link, a cluster or accordion group is a heading with no page of its own so it reads as text, and the current page is the emphasized leaf. The trail is also the way back, which removes the separate back link rather than moving it: a record page and a record form are not navigation entries themselves, so each declares the list it belongs to and that list joins the trail as an ordinary link, one click from the page. The depth rule is restated as a fact rather than a feel: a page whose whole path is its cluster and itself gets no trail, and three segments or more earns the line, which added trails to two more template pages and removed the three stacked back links. **And a button's icon rides on its label.** The template pinned every icon to 15px regardless of the button and never set `line-height`, so the text box was taller than the glyph and the two sat off each other's centre line. | **v2026.14.0** | 17 August 2026 | Settle three UI behaviors that were being decided per screen, and that a screen review found missing on a real one. First, data entry is page-hosted: a create, edit, multi-step, or settings form is its own route or a form region on the current page, inside the shell, and never a modal, a drawer, or an off-canvas panel, however few fields it has. A modal keeps what it is for, a decision that must be answered now, and may carry at most about three fields when those fields are the decision itself, such as a typed confirm word, a reason, or a new date. So the sanctioned form modal, the complex data-entry modal, the wizard in a modal, and the whole segmented tabbed form modal are gone from `modals-dialogs.md`, and the `modal-form-*` classes are renamed to `form-tab*` so nothing invites a form back into a dialog. Second, a step-by-step form no longer holds the user's work in the browser. The advance button is `Continue`: it validates the step, saves the entered values server-side as a draft, then advances, so a closed tab, an expired session, a dropped connection, a flat battery, or a switch to another machine costs nothing already entered, and a failed save keeps every value on the step with a retryable error rather than swallowing it. Returning resumes at the saved step with the earlier ones restored, reachable from a standing surface rather than a remembered URL. Where the draft lives stays the developer's decision, a separate draft table or the record's own table with a draft state, and the trade-off is named rather than chosen quietly, since a draft in the live table needs its required columns nullable until completion; either way a draft is not a record, so it is authorized to its owner, closed out in the transaction that commits the record, kept out of counts, exports and reports, and never holds a credential. Third, every list sorts and filters. Sorting existed but was hedged into "where applicable", and the filter bar was written as optional, so both were being skipped: now every orderable column sorts, every list declares a default sort, and a search and filter bar carries one facet per dimension the list is narrowed by, read from the columns' codified reference sets. The rules that make those work are stated rather than assumed: both run over the whole result set, server-side where the list is paginated, so a filter finds the matches on page three instead of reordering the twenty-five rows on screen; any change returns to page one; both counts report the filtered total; and the state lives in the URL query so a refresh, the back button, and a shared link reproduce the view. Adds two mandatory sections to `ui-ux-quality.md` (Data Entry Is Page-Hosted, Step-By-Step Form Drafts), a third for lists (Every List Sorts And Filters), and a new `4a` section to the tables reference. Wiring: five new hard stops, the always-on UI invariant in the loader, new list and draft knobs plus per-entity default sort and facets in `PROJECT-CONTEXT.md`, a draft-versus-record grain bullet in `semantic-data-model.md`, and updates to `forms.md`, `modals-dialogs.md`, `tables.md`, `search-filter.md`, `buttons.md`, the UI skill index, `catalog-ui.md`, `README.md`, both developer-handbook guides, and `PROJECT-CONTEXT-UNDERSTANDING.md`. The layout template was demonstrating the opposite, so its two working lists gained sortable headers, honest filtered counts in place of a fabricated total, and announced result counts, while the two static illustrations say plainly that they are abbreviated rather than shipping dead controls. Three adversarial review rounds over the change found eighteen defects in it, all fixed before release, including a surviving rich-editor-in-a-modal loophole, a tablist whose children were not tabs, a draft rule that contradicted itself on list counts, and a handbook that claimed to document every intake field while missing four new ones. |
| **v2026.13.0** | 17 August 2026 | Make the code review and security review run on every delivered code change, without the developer asking. The reviewers already existed and were dormant: `code-reviewer` and `security-reviewer` had no reference anywhere outside their own files, no gate fired them, no command ran them, and `verified-closeout` (the command whose entire job is "before calling work done") had eleven process steps and nine return items, not one of which was a review.
