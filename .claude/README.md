# Claude AI Agent

> Gateway version: v2026.21.0 (3 November 2026). Full history: `.claude/CHANGELOG.md`.

This folder is the core of the Claude-only AI-agent gateway for a repository. The gateway ships as the root `CLAUDE.md` plus three folders: this `.claude/` folder, `doc/`, and `scripts/`. The infra team provides them at the root of each new project repository, beside the environment branches, and the project starts from zero with `/fresh-project-start`. `.claude/` holds required project context, rules, commands, subagents, and skills; `doc/` and `scripts/` hold the requirement intake, planning, task tracking, and core repo structure listed under Shipped Beside This Folder.

## Read Order For Claude

1. `.claude/PROJECT-CONTEXT.md`.
2. `.claude/rules/hard-stops.md` first, for the conditions that require Claude to stop and ask. Those stops bind every user in every session; only a session verified against `.claude/OVERRIDE-AUTHORITY.md` can lift one, per `rules/owner-override.md`.
3. Core rules: `fresh-project-gateway.md`, `project-intake.md`, `deployment.md`, `enterprise-governance.md`, `production-readiness.md`, `secret-handling.md`, `feedback-logging.md`, `eod-reporting.md`, `orientation-map.md`. Three of these run every session in the background: feedback logging (log when a developer presses the same unmet request about three times), EOD reporting (write the day's status report to `doc/eod/` as the work happens), and the orientation map (rebuild the owner's one-page project map when a milestone, a task status, the configuration surface, or an open item moves). Add task-specific rules:
   - code work: `code-documentation.md`, `secure-coding.md` (server-side validation, input kept from becoming syntax, output encoding, CSRF and cookies, no unsafe deserialization, outbound calls and supplied URLs, uploads, error display, the security audit trail, and the tests that prove them), plus `review-gates.md` (the code review and security review passes both run before any delivered change is called done)
   - Git branching / PR / release / tag work: `git-branching-release.md`
   - any UI: `ui-ux-quality.md` (the authoritative UI standard) plus the bundled `ui-ux-design` skill at `.claude/skills/ui-ux-design/` (values in `reference/design-tokens.md`, assets in `assets/`). Every app reproduces the same look and feel; only the app name, title-bar name, navigation tree, brand-assets path, UI stack, feature toggles, entities, roles, and domain copy vary per project, and the in-project asset destination is asked, never chosen. Every UI change is verified against the reference layout template in `00-read-first/05-layout-template/` with `/ui-verify` before it is called done.
   - sign-in, sign-out, sessions, roles, permissions, or any per-feature access check: the Role And Access Model section of `ui-ux-quality.md`, then `secure-coding.md` and `enterprise-governance.md`. Authentication follows the application's own authentication model as recorded in `PROJECT-CONTEXT.md`; each app provides its own authorization, resolved per feature.
   - implementation / multi-phase work: `phased-workflow.md`, which hands the lifecycle to `solution-development-kit.md`
   - requirement intake, solution and phase planning, task tracking, or work on a Task ID: `solution-development-kit.md` (the authority for those, superseding the overlapping parts of `phased-workflow.md` and the task-status parts of `eod-reporting.md`) plus the bundled `generate-phase-plan`, `generate-project-tasks`, and `execute-approved-task` skills and their agents. Requirements come from `doc/solutiondocument/`, the plan goes to `doc/phasedocument/`, task status lives in `doc/tasktracking/`, and the compact living project memory lives in `doc/corerepo/`.
   - a service interface is exposed or consumed: `api-design.md`
   - a call crosses a process or network boundary: `resilience.md`
   - data is stored beyond transient request state: `data-governance.md`
   - a persisted data structure is designed or altered, or a data model, ERD, or a feature's analytics is planned: `semantic-data-model.md` (the authoritative rule) plus the bundled `semantic-data-model` skill at `.claude/skills/semantic-data-model/` (question set, grain and keys, measures and dimensions, history and outcomes, time and units, the ERD and semantic hand-off, a worked example). The confirmed analytics questions come before the shape, every table declares what one row means, and the change ships its ERD and semantic hand-off.
   - a production service runs: `operations-incident.md`
   - runtime LLM or agent behavior ships: `ai-agent-governance.md`, then `ai-guardrails.md` (the checks between a user's input and the model, and between the model's output and where it lands)
   - the app calls an AI model at runtime, or a provider/model/catalog screen changes: `ai-model-catalog.md` (the authoritative rule) plus the bundled `ai-model-integration` skill at `.claude/skills/ai-model-integration/` (record shape, placeholder contract, engine, response paths, cost, masking, provider matrix, catalog UI, guardrails, multi-call orchestration, AI admin screens). One record per model, one generic engine, the API key on the record, no per-provider branch.
4. Database/schema work: read `.claude/rules/database-schema.md` in full.
5. Deployment work: read `.claude/rules/deployment.md` before touching layout, entry points, assets, deploy scripts, hosting settings, infrastructure, or release instructions.
6. Read existing repo docs and knowledge-base files before editing; for cross-session continuity see `.claude/rules/knowledge-base.md`.
7. Use `.claude/commands/` for fresh-project start, intake, data-model planning, deployment checks, database tasks, and verified closeout.

## What This Folder Contains

- `PROJECT-CONTEXT.md`: required non-secret project, stack, deployment, and database context.
- `OVERRIDE-AUTHORITY.md`: the hashed identity list allowed to override a rule (see `rules/owner-override.md`). Digests only, never addresses.
- `settings.json`: safe defaults for Claude Code permissions.
- `feedback-logs/`: automatic improvement feedback (see `rules/feedback-logging.md`).
- `rules/`: core rules plus conditional rules that apply only when their gate matches (`solution-development-kit.md`, `database-schema.md`, `api-design.md`, `resilience.md`, `data-governance.md`, `semantic-data-model.md`, `operations-incident.md`, `ai-agent-governance.md`, `ai-guardrails.md`, `ai-model-catalog.md`).
- `commands/`: one slash command per workflow, so nobody writes a prompt by hand. `fresh-project-start.md` for a new project; `project-intake.md` for repeatable intake; `semantic-model-plan.md` for data-model planning; `database-task.md` for database work; `document-code.md` for code documentation; `deployment-check.md` for deployment readiness; `security-check.md` for an on-demand security review; `verified-closeout.md` for the final validation and report; `owner-override.md` for the verified-owner override request; `eod.md` to close out, review, or correct the day's status report; `orientation-map.md` to build, refresh, or check the owner's one-page project map; `day-start.md` to open a working session on a Task ID; `session-handoff.md` to hand work across a session, a day, or a developer; `account-handover.md` to move in-flight work to a different Claude account; `git-workflow.md` for Git and GitHub workflows from sync to release; `ui-verify.md` to compare a developed screen with the reference layout template and fix every mismatch.
- `agents/`: specialized subagents for review, database planning, security, testing, and release readiness. `code-reviewer` and `security-reviewer` are not optional extras: `rules/review-gates.md` runs both over every delivered code change before it can be called done. The solution development kit adds sixteen more: `standards-reader`, `solution-reader`, `requirement-analyst`, `gap-auditor`, `solution-architect`, `dependency-planner`, `phase-planner`, `qa-reviewer`, and `phase-orchestrator` for phase planning; `task-planner` and `progress-tracker` for the task backlog, its progress, and its timing; `task-execution-orchestrator`, `data-design-reviewer`, and `acceptance-gate` for executing one approved task; `infra-readiness-agent` for the Phase 1 infrastructure baseline and every material infrastructure change; and `core-repo-maintainer` for the persistent core repo in `doc/corerepo/`.
- `skills/ui-ux-design/`: the approved design system - component guidelines, the token specification (`reference/design-tokens.md`), and the CLaaS2SaaS brand asset pack (`assets/`).
- `skills/ai-model-integration/`: the approved AI model integration pattern - the catalog record shape, placeholder and substitution contract, the generic request engine, response-path hand-off, cost and usage, credential handling and masking, a worked provider matrix, the catalog UI, the guardrail pipeline (`reference/guardrails.md`), multi-call orchestration (`reference/orchestration.md`), and the AI admin screens and AI output patterns (`reference/ai-admin-ui.md`).
- `skills/semantic-data-model/`: the approved data-structure pattern - the analytics question set, grain and keys, measures and dimensions, history and outcome capture, time and units, the ERD and semantic hand-off, and a worked contact-management example.
- `skills/generate-phase-plan/`: `/generate-phase-plan` - reads the live standards and every active requirement under `doc/solutiondocument/`, writes the planning package to `doc/phasedocument/`, and stops for human approval. Planning only.
- `skills/generate-project-tasks/`: `/generate-project-tasks` - after both planning documents are approved, turns the phase plan into the `Phase -> Module/Menu or Workstream -> Task -> Subtask` backlog in `doc/tasktracking/`, with traceability and the event log.
- `skills/execute-approved-task/`: `/execute-approved-task <TASK-ID>` - runs one approved task through Gates 1 to 6, from plan and design approval through the data and schema gates, coding authorization, implementation, and user acceptance.

## Shipped Beside This Folder

These sit at the project root, next to `.claude/`.

Shipped:

- `CLAUDE.md`: the loader Claude reads at startup.
- `doc/solutiondocument/`: the intake for approved solution requirements, in category folders the planning agents discover at run time. An `Archive` folder is ignored unless an active source references it or a human re-approves it.
- `doc/phasedocument/`: the planning package `/generate-phase-plan` writes, including `PROJECT_STANDARDS_BASELINE.md`, `02_Gap_Conflict_Report.md`, and `MASTER_PHASE_PLAN.md`.
- `doc/tasktracking/`: the task register, task board, traceability matrix, append-only event log, completion log, and per-task data design evidence.
- `doc/corerepo/`: the compact, vendor-neutral living project memory, maintained by `core-repo-maintainer` on accepted or verified state changes - current state, infrastructure readiness, feature and requirement coverage, a code map, the verified data and entity models, the integration and AI registers, a task status snapshot, the decision and conflict register, the change log, the handover, and a short AI context and manifest that a task reads first. It maps to the requirements and snapshots task status, and owns neither.
- `scripts/task-event.sh`: appends a timestamped task lifecycle event to `doc/tasktracking/task-events.jsonl`.

Created on first use:

- `doc/eod/`: the daily EOD reports (see `rules/eod-reporting.md`).
- `doc/orientation-map.html`: the default path for the owner's one-page project map, built once its path and reader are confirmed (see `rules/orientation-map.md`).
- `doc/knowledge-base/`: the default knowledge-base root when the project has none of its own, created only after the developer approves the first entry (see `rules/knowledge-base.md`).

## Key Workflows

- Startup: on a fresh project, start from `.claude/commands/fresh-project-start.md`. Ask what to build, how, which stack/versions, hosting/deployment, database details, and how success is validated. Keep asking until the task is clear enough to implement, validate, explain, and deploy safely. Durable non-secret answers go in `.claude/PROJECT-CONTEXT.md` after confirmation. Secrets never go in this folder.
- Solution planning and task tracking: requirements go in `doc/solutiondocument/`. `/generate-phase-plan` reads them with the live standards, gives every requirement, feature, and function a disposition so nothing disappears silently, runs the Phase 1 infrastructure baseline, writes the planning package to `doc/phasedocument/` in at most five macro phases (platform and infrastructure foundation; the core application with sign-in, per-feature authorization, administration, and the AI model catalog where AI is in scope; feature design; feature build; and UAT and release readiness), and stops; no application code is written until a human explicitly approves `02_Gap_Conflict_Report.md` and `MASTER_PHASE_PLAN.md`, and an unresolved material conflict or gap blocks the work it affects. `/generate-project-tasks` then builds the backlog in `doc/tasktracking/`, organized `Phase -> Module/Menu or Workstream -> Task -> Subtask` under stable Task IDs that are never renumbered once published, and every task states its Frontend, Backend, Database, Integration/API, AI, Security, tests, acceptance, indexing, and idempotency work, or `Not Applicable - Verified` with the reason. `/execute-approved-task <TASK-ID>` runs one task at a time through six gates: plan and design approval; a logical data proposal; a physical proposal checked against the project's schema source; the migration and the schema self-check, recorded as `SCHEMA VERIFIED`; explicit coding authorization and implementation; and user testing. The three data gates apply only when the task touches persisted structures. A task moves `Planned -> Ready -> In Progress -> Implementation Complete -> User Testing -> Accepted`, and only explicit user testing approval makes it `Accepted`. `scripts/task-event.sh` records each event with a real timestamp, so time is measured, never guessed. `doc/corerepo/` keeps the project's compact living memory, updated incrementally on accepted or verified changes, and a task starts from its `14_AI_CONTEXT.md` and `PROJECT_MANIFEST.yaml` rather than from a full reread of the repository. A kit upgrade in an existing project is governance maintenance only: it keeps every published Task ID, event, and acceptance record, writes no code, schema, or deployment, and merges only after a post-upgrade validation passes. See `rules/solution-development-kit.md`.
- Override: the rules bind every user in every session and in every project this folder is copied into. Only a session Claude verifies against `OVERRIDE-AUTHORITY.md` can lift one named rule for one named action. Claude resolves the identity itself from a secret only one person holds, never from a claim, a typed address, `git config`, or a credential the team shares, and never discloses it. See `rules/owner-override.md`.
- Clarification: never assume unclear requirements, context, deployment, schema, credentials, validation, or intent. This is a hard stop - do not implement, edit, run commands, update context, write deployment steps, touch schema, or claim completion until unclear points are answered.
- Database schema: mandatory for schema and database-backed code. The project's own schema is the source of truth, read from the source recorded in `PROJECT-CONTEXT.md`: no DDL executed directly; no invented names; check existing tables first; show the exact shape and get explicit confirmation before a migration is written through the confirmed migration tool; stop if the schema source cannot be read. See `rules/database-schema.md`.
- Data model: a table is designed for the questions it will be asked, not only for the screen. Confirm the feature's analytics question set first, declare what one row means, keep the atomic rows instead of stored totals, group by codified dimensions reused from the platform rather than free text, and record state changes, step outcomes, failures, and duplicates as rows instead of overwriting them. The change ships the data structure, entity relationships, ERD, and semantic hand-off as metadata, and adds no warehouse, cube, or second reporting store. `/semantic-model-plan` runs the question set, the reuse search, and the shape preview in order. See `rules/semantic-data-model.md`.
- Lists and tables: every list / index screen sorts and filters. Every orderable column sorts, the list opens on a declared default sort, and a search and filter bar sits above it with a facet per dimension the list is narrowed by. Both run over the whole result set, on the server where the list is paginated, so the matches on page three are reachable; any change returns to page one, both counts report the filtered total, and the sort, filters, and page live in the URL query so a refresh or a shared link reproduces the view. See `rules/ui-ux-quality.md` and `skills/ui-ux-design/reference/tables.md`.
- Buttons and row actions: a button role has one look. There is one solid action per group, the group's main one, and one neutral secondary look for every other labeled action, so `Cancel`, `Clear`, `Reset`, `Back`, and `Apply` are the same control on every screen; a borderless or outlined labeled button does not exist, a filter bar has no solid button at all, and a control's look never changes with its state. Every actions-column control carries its visible word beside the icon (`View`, `Edit`, `Delete`), keeps it on a narrow screen, and moves past the third action into one labeled `More` overflow. Icon-only is chrome, on a closed list. See `rules/ui-ux-quality.md` and `skills/ui-ux-design/reference/buttons.md`.
- Forms and data entry: data entry lives in the application's own UI, never in a popup. A create, edit, multi-step, or settings form is its own route or a form region on the current page, and a modal is kept for a decision that must be answered now, carrying at most the few fields that are the decision itself. Errors report once, where they are: each message inline under its own field, a blocked submit announced by one error toast naming how many fields need attention with focus moved to the first invalid field, no summary card repeating them, and one inline alert at the form foot for a form-level error that belongs to no field. Every confirmation is the kit's own dialog, never the browser's native `confirm`, `prompt`, or `alert`, and a disabled control shows its reason beside it, never only in a hover tooltip. Every single yes/no value is a switch with a visible state word, whether it applies instantly or saves with the form, and a checkbox is only for picking several items from a set. A step-by-step form advances on `Continue`, which validates the step, saves it server-side as a resumable draft, then moves on, so a closed tab, an expired session, or another machine costs nothing already entered; a failed save keeps the values and stays put. Where the draft is stored is the developer's decision, a separate draft table or the record's own table with a draft state, and a draft is never a record in a list, a count, or a report, and never holds a credential. See `rules/ui-ux-quality.md` and `skills/ui-ux-design/reference/forms.md`.
- Feedback: every toast appears at the **top right**, in one host offset below the top bar, newest nearest the top edge. That is the only placement: no bottom-right, no top-center, no per-screen or per-type choice, and a narrow screen widens the same top edge rather than moving to another corner. The polite and assertive live regions sit inside that one host, so politeness decides how a message is announced and never where it shows up. See `rules/ui-ux-quality.md` and `skills/ui-ux-design/reference/toasts.md`.
- Reference layout check: the template in `00-read-first/05-layout-template/` is the reference implementation of the UI rule. Before UI work is called done, `/ui-verify` compares every screen added or changed with the template screen of the same archetype, as a browser comparison where a browser tool and the running app are available and a static token and markup comparison always. The comparison is exact to a fraction of a pixel. Every mismatch is flagged in the report and the final summary, then fixed and verified again, or recorded as a documented exception the developer authorized in words, and a static-only check is reported as such, never as a visual match. Existing apps are covered too: `/ui-verify all` audits every screen when the kit first lands in an app or a kit upgrade changes the UI standard. See `rules/ui-ux-quality.md` and `commands/ui-verify.md`.
- AI model calls: a model is a catalog record, not code. One record holds the endpoint, headers, typed body fields, response paths, price, and its own masked API key; one generic engine reads it, so a new model is a new record and never a code change or a provider branch. Placeholders are `{{prompt}}`, `{{api_key}}`, and `{{env.NAME}}`. A saved key is never re-rendered or logged, the raw response stays reachable when a response path misses, cost reports unknown rather than zero, and a record becomes callable only after a real test call passes. A record uses the provider's dated snapshot model id, never a moving alias, and carries its lifecycle state and retirement date. A replacement model is a new record that takes production traffic only after its eval set passes, every route change is gated on a recorded eval result per step, record, and prompt version, and a provider's own in-call fallback option is never set. The two screens sit first in the System Administration `AI` group, beside the AI routing, guardrail, limit, and kill switch screens, and `Integrations` keeps only the non-AI connections. AI screens under Compliance are view-only, and AI pauses and the feedback queue sit in Application Administration > AI Oversight. See `rules/ai-model-catalog.md`.
- AI guardrails: every AI feature puts a confirmed set of checks between the user and the model, run cheapest first, and checks model output before it lands anywhere, except in the confirmed retractable streaming mode, where shown text can be taken back. Uploads, retrieved chunks, and tool results reach the model as data, never as instructions, and retrieval is filtered to the user's own scope in the data layer. No secret and no authorization logic sits in a prompt, and an agent's tool call runs as the requesting user. Images in model output are never rendered automatically, and a link renders only when its destination is on the confirmed allow-list or traces to a source the application supplied. Each check has a confirmed fail mode, and a degraded one is never silent. Limits cover the whole workflow, not only one call, and every AI feature has its own kill switch with a non-AI fallback. No model that drafted or judged content decides whether it is accepted. AI content carries the confirmed AI label, and the AI admin screens sit in the four clusters on the existing archetypes. See `rules/ai-guardrails.md` and `skills/ai-model-integration/reference/guardrails.md`.
- Authentication and authorization: authentication follows the application's own authentication model as recorded in `PROJECT-CONTEXT.md`. Authorization belongs to the application: a feature registry with stable codes, roles expressed as sets of feature grants, and every grant enforced at all four layers, navigation, handler, per-record policy, and query scope. Grants are data an administrator changes in the UI, never a constant in code and never a deployment, and a user with no local record yet is a first login rather than a refusal. No save may leave the app without an active system administrator, and deactivating a local user ends their access and their sessions on the next request. See the Role And Access Model section of `rules/ui-ux-quality.md`.
- Deployment: no default model. Ask what source control, CI/CD, hosting, deployment target, runtime, build, artifact flow, data services, background processing, and operations apply. Provider- and stack-specific rules apply only after the developer confirms them. See `rules/deployment.md`.
- Knowledge base: read `PROJECT-CONTEXT.md` and repo knowledge-base files before editing. After each completed implementation (validation run or limitation documented), prompt the developer to create/update the knowledge base now or defer; write only after explicit approval. It is living documentation, kept in sync behind the same gate. See `rules/knowledge-base.md`.
- Secure coding: every delivered code change is written so the common attacks do not land, without the developer asking. The server validates every input and the browser's validation is only a courtesy to the user; a request is bound to named fields, never mass-assigned. Values reach a database as bound parameters, and a sort column or other identifier taken from a request is checked against an allow-list, which matters because every list sorts from the URL. Output is escaped for where it lands, including exports and email, rich content goes through the confirmed sanitizer or renders as text, and a response carries only its listed fields. CSRF stays on for every state-changing cookie-authenticated route, signature-verified webhooks are the only standing exemption, and no `GET` changes application data or access outside the local-deactivation teardown and the request's own audit record. Untrusted data is never deserialized into objects or executed, TLS verification is never turned off, the server never fetches a supplied URL at an internal address the environment configuration does not name, and a browser is redirected only to the application's own routes or registered URLs. An upload is checked by its content, stored under a generated name outside the web root, served as a download when it can carry active content, and authorized like its record. Production runs with debug output off, so an unexpected error shows a generic message and a correlation id. Every security-relevant action a change adds or alters, refused attempts included, leaves an append-only audit record with no secret in it, and the change ships tests for the controls it adds or alters. A dependency with a known critical, high, or unrated advisory is not taken unless the fixed version is used or the risk is accepted and recorded. Nothing is ever described as SOC 2, ISO 27001, or otherwise compliant because of its code; the report names the control and the requirement it supports. See `rules/secure-coding.md`.
- Review gates: every delivered code change gets two passes before it is called done, without the developer asking for them. The `code-reviewer` subagent asks whether it is correct, complete, and in the project's patterns; the `security-reviewer` subagent asks whether it can be abused, leaks, or trusts something it should not. Both run as subagents over the actual diff, because a reviewer sharing the author's context inherits the author's blind spot. Every finding is rated `Critical`, `High`, `Medium`, or `Low`: the first two block the done claim until fixed and re-reviewed, or explicitly signed off by the developer and recorded as an exception. Depth scales with what the change touches; whether the pass ran does not, and a clean pass is stated rather than passed over in silence. `/security-check` runs the security pass on demand. See `rules/review-gates.md`.
- EOD reporting: the day's status report writes itself. At the first substantive prompt of a session, Claude opens or creates today's report at `doc/eod/eod-date-<D><Month><YYYY>.md` (for example `eod-date-17August2026.md`) and asks in one message whose EOD this is and what they plan to do, then updates each task's status as it reaches an outcome. It asks rather than infers, because on a shared plan the account, its email, and the GitHub login are the same for everyone and `git config` is editable; the name is matched to the `## Team` table in `PROJECT-CONTEXT.md` for the developer's email, role code, and section position. One file per day, one `## Developer Name (ROLE)` section per developer, four summary lines over a task table whose status comes from a closed list and whose `Started` and `Completed` columns say when each task began and finished, dated so a task that started last week still reads correctly. It is a status report, not a handoff and not a time sheet: those two timestamps mark the task rather than the person, and are never totalled into hours or a rate. No measured hours, no activity, no customer data. A tracked task's row carries its Task ID, and an EOD `Done` never makes a tracked task `Accepted`. Written all day, committed at close. Use `/eod` to close out, review the team's day, or correct an entry. See `rules/eod-reporting.md`.
- Orientation map: one page for whoever owns the project, kept current without anybody asking for it. It answers three questions in order: where the work stands and roughly how far through it is (Position), what the owner has to care about and what they can ignore, naming real files (Surface), and what is unresolved, with the decisions only they can make split from the work Claude can do (Open). Claude rebuilds it from the repository when a trigger fires - a milestone or phase accepted, the Phase Plan approved, a task changing status in `doc/tasktracking/`, a file added to or removed from the configuration surface, a blocker opened or resolved, an exception recorded - and not on ordinary commits, because a page rewritten on every push stops being a signal that anything moved. It is a snapshot, not a dashboard: it reads nothing at runtime, reloading it changes nothing, and it carries its date and the commit it was generated from. It holds no fact of its own, so a line on it that exists nowhere else is a defect. A refresh reports the difference, and says outright when something previously open has closed. Use `/orientation-map` to build, refresh, or check it. See `rules/orientation-map.md`.
- Documentation: when writing/editing code, add docstrings per `rules/code-documentation.md`; use `commands/document-code.md` to add or audit documentation.
